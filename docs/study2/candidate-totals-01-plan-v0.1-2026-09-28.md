# CANDIDATE-TOTALS-01：予測合計を添えると、本人判断を保った共同案を選べるか

2026-09-28／設計案v0.1、略号CT01。[FC02の結果](../../experiments/FC02/docs/feasible-choice-02-result-2026-09-28.md)を受けた小比較。**同じ二候補に計算済みの予測合計を添え、適切な共同提案が増えるか、その提案が相手の確認・二人の利用まで届くか**を測る。

今回の作業は設計・入力材料・算術点検・取得前カードまで。実モデル生成0。Colabで丸ごと一セル実行するコードは次工程で作る。

## 1. 今回確かめること

FC02では、候補選択の本人判断と参照は全件正しかったが、共同案の適切な提案は19/32、合意・利用までの成立は18/32だった。候補の複製は正確でも、合法な二案から非最適側を13件選んだ。本人が共同では相手へ譲る必要のある8条件でも、適切な提案2/8、全工程1/8だった。

そこで、モデルへ渡す判断材料に**二案の予測合計だけを追加**する。経験から人数を集計する処理はコードで行い、どちらの候補を選ぶか、本人は何を推奨するか、どの経験を根拠とするかはモデルが答える。

検証する予想は「合計を供給すると、本人判断を保った適切な共同提案が増える」。FC02の誤りを計算ミスと診断済みではない。合計表は正しい選択に必要な派生情報を意図的に供給する介入であり、改善してもモデル内部の原因を算術だけに特定したとはしない。

## 2. 比較は候補選択方式の二条件に絞る

| 項目 | 合計なし BASE | 合計あり TOTALS |
|---|---|---|
| 全経験5行・以前の本人判断・旧共同記録 | 共通 | 共通 |
| 候補のID・順序・A/B割付 | 共通 | 共通 |
| 候補ごとの予測合計 | なし | 各候補に一つの数値を追加 |
| 本人欄・候補ID・経験参照 | モデルが生成 | 同じ形式でモデルが生成 |
| 保存時の処理 | 選ばれた割付を複製 | 同じ複製処理 |
| 相手の確認・二人の後続利用 | 共通手順 | 共通手順 |

**両条件とも今回新しく生成する。** FC02のSELECT19/32を対照群の回答として流用しない。直接記述との比較は今回は行わず、候補選択方式の中で集計情報を供給する差へ絞る。

全32材料を使用する。FC02で失敗した13件だけを選ばず、成功・失敗を含む16出発点×反転／補強の全条件を保持する。弱／強、本人推奨一致／不一致、旧合意15出発点／未合意M05も維持する。FC02の生成した提案・確認・利用は今回の入力にしない。

今回は既知材料への支援効果を調べる適応的比較であり、未使用材料への再現試験とは呼ばない。

## 3. 追加する数値を固定する

候補cの合計は、実際の入力経験行から次の式で計算する。

`合計(c) = Σ役r [40 × rの割付媒体の全回成功人数 ÷ rの全回試行人数]`

更新した本人は累計80人、相手は累計40人なので、両方を次回40人に換算してから足す。分数で計算し、今回の64候補値がすべて整数になることを確認した。平均の丸め・生人数の単純合計は使わない。

各候補に `projected_total_success_per_40_each` を一つだけ加える。候補の並びを点数順へ変更せず、「最適」「推奨」などのラベルも付けない。各役別の計算内訳や本人の正解推奨は入力へ追加しない。**モデルには合計の大小が見えるので、求める能力は集計支援を受けた選択である。**

例：M01補強では、Aは紙24／デジタル21、Bは紙27／デジタル23の予測で、本人の推奨は双方紙。TOTALSの候補表は次のとおり。

```json
[
  {"candidate_id":"X","allocation":{"A":"DIGITAL","B":"PAPER"},"projected_total_success_per_40_each":48},
  {"candidate_id":"Y","allocation":{"A":"PAPER","B":"DIGITAL"},"projected_total_success_per_40_each":47}
]
```

BASEは同じ二行から追加数値欄だけを除いた表を見る。両条件に共通の提案指示として、追加欄があれば各区画40人当たりの予測合計であり、新しい観測ではないと一文定義する。他の提案指示・出力schemaはFC02のSELECTを継承する。本人欄の参照は自分の全経験ID、提案の参照は二人の五経験IDのまま。集計値のための新しい証拠IDは作らない。

計算器の入力行hash、役別分母・成功人数、候補別計算結果、追加前後の候補表hashを保存する。保存器は選択されたIDの割付だけを複製し、最大値の候補へ選び直す処理は持たない。

## 4. 合計を見せるのは最初の提案だけ

1. **提案 PROPOSE**：更新本人が、本人判断と候補IDを答える。TOTALSだけ候補合計を見る。
2. **相手確認 CONFIRM**：相手が共通形式の実提案を受け、本人判断とACCEPT／COUNTER／HOLDを返す。
3. **利用 USE-A／USE-B**：二人が実提案・実確認から、本人判断と共同担当／共同保留を答える。

確認・利用では全経験5行を共通に再掲するが、候補表・候補ID・予測合計・介入名・採点結果は渡さない。確認・利用の指示とschemaはFC02と同一。本人欄や参照の意味修理、資源違反の自動消去、正しい対案への自動承認は加えない。

これにより、まず「計算済み合計が提案の選択を助けたか」、次に「その生成物が共通の後続手順でどう扱われたか」を読める。後続は条件ごとに異なる実提案を受けるため、確認工程に対する独立の介入効果とはしない。

合意Kは、別役による正しい返信先へのACCEPT、提案との割付一致、資源適合が成立すること。最適性はKに含めず、現在最適な合意Cで評価する。正しいCOUNTERは適切な応答として数えるが、今回も再承認工程を設けないためKにはならない。

## 5. 提示順と実行順をそろえる

FC02の候補ID・順序を保持する。強弱×本人推奨一致／不一致×反転／補強の各4条件で、正解ID（X/Y）×位置（先頭/二番目）の四組合せが一つずつ入る。両条件で同じ表順を使う。

条件先行順はFC02の方式先行順を、DIRECT→BASE、SELECT→TOTALSへ対応させる。これは既存の配置規則を継承するもので、FC02の結果で並べ替えない。上記8区分でBASE先行／TOTALS先行が2対2。各条件は別コンテキストで実行し、別条件の回答を渡さない。

seed基準は2026092806。配置ブロック×元履歴集合×役×工程から算出し、BASE/TOTALS・反転/補強・プロフィールを除く。対応二条件のseedは同じだが、入力の差による出力のゆらぎが相殺される保証とはしない。新記録IDはCT01のnamespaceを使い、旧記録との衝突がなく、介入名や正解を露出しないことを接続準備で点検する。

## 6. 主比較と工程別の評価

主比較は**適切提案PのTOTALS−BASE差**。Pは本人判断L、本人経験の参照Z_local、共同案の現在最適性O、共同の経験参照がすべて適合した提案とする。共同だけ正しければ成功とは数えない。

| 指標 | 各条件の分母 | 内容 |
|---|---:|---|
| F／O／P | 各32提案 | 実行可能／現在最適／本人と共同・根拠の両立 |
| L／Z | 提案32・確認32・利用64 | 本人判断と工程ごとの根拠・共同状態の宣言 |
| K／C | 各32経路 | 合意の成立／現在最適な合意 |
| H／後続現在最適性 | 各64回答 | 合意への忠実な利用・適切保留／現在の最適割付 |
| J | 32経路 | 同一条件の全工程で本人・共同・根拠が成立 |
| Q | 16出発点 | 反転・補強のJがともに成立 |
| S_target／I_peer | 各16出発点 | 両経験条件の形成・利用で本人を適切に更新／相手判断を保持 |

全体に加え、強弱、本人推奨一致／不一致、反転／補強、元履歴集合、旧合意からの変更／維持／新形成、および強弱×推奨一致×経験条件の8区分を固定して表示する。とくに**弱かつ同推奨の8条件**で本人の推奨と共同の担当を使い分けられるかを見る。

提案から確認への挙動も先に分けて数える。ここで提案を分ける基準は、**共同割付の現在最適性O**とする。本人欄や参照の不備を含む総合Pとは区別し、たとえば共同割付が正しく本人欄だけ誤った提案へのACCEPTを、割付への不適切な承認とは数えない。応答の適合は、FC02のaction_contractと返信先・共同経験参照を合わせたappropriate_responseを継承する。

- 最適な共同提案（O成立）への適切なACCEPT／不適切な応答。
- 非最適な共同提案（O不成立）への適切なCOUNTERまたはHOLD／不適切な応答。
- 提案適合Pから合意適合Cへ失われた経路、および本人Lや参照Zの不備。

各分類は実際に該当した提案数を分母として併記する。入力提案や応答が欠測なら未確定を別記し、応答の既知不適合と混ぜない。条件により該当提案自体が変わるため、その割合だけで確認能力の優劣を結論しない。ゼロ件なら該当なしとする。未合意時のHも、実際に生じた経路数とともに報告する。

## 7. 提案の改善と、全工程の到達を分けて判定する

**方向予想**はP_TOTALS > P_BASE。対応内訳（両方成立／BASEのみ／TOTALSのみ／双方不成立／未確定）と差を出す。差ゼロ・逆方向も同じ規則で閉じる。

実用上の次工程を選ぶ目安は二段にする。TOTALSを対象とし、BASEにも同じ基準を当てる。

1. **提案目安**：P≥28/32、弱×同推奨P≥7/8、提案時の本人L=32/32・Z_local=32/32。総数では改善していても、本人欄の崩れや譲歩条件の不成立を隠さない。
2. **全工程目安**：FC02の基準を継承し、Q≥14/16、各元履歴集合Q≥7/8、弱・強各Q≥7/8、S_target=I_peer=16/16。

提案目安の28/32・7/8は、この小比較で次へ進むために事前に選んだ7/8水準であり、推定精度や有意差を保証する基準ではない。全工程目安を下げて前段改善を成功扱いするのではなく、別々の到達点として並記する。

各基準の成立下限がすべて届けばMET_IN_FIXED_SAMPLE、どれかの上限でも届かなければNOT_MET、それ以外はINCONCLUSIVE。P差が正でも目安未達なら部分的改善、両条件が目安達成で差ゼロなら今回の合計追加の優位は確認しなかったとする。

## 8. 欠測・保存・推論の境界

EOS・構造の不備は取得欠測、親回答を渡せない場合は依存欠測。未知候補IDはP/Oの既知不成立として残し、後続は依存欠測。UNDECIDEDは両者UNDECIDEDとして運ぶが、最適提案とは数えない。意味上不適切でも受渡し可能なら続行する。

必要成分が欠測なら合成指標は未確定、既知の成分不備も別保存。各予定分母で成立／不成立／未確定を並べる。P差の欠測下限は`(T成立−B成立−B未確定)/32`、上限は`(T成立＋T未確定−B成立)/32`。信頼区間ではない。生JSON優先・既知の完全外装だけ除去する規則を継承し、内容修理・追加生成で埋めない。

既知の16履歴に二経験条件と二介入を対応させるため、32条件を独立標本と見なさない。元履歴集合1/2は新しい同一入力反復ではない。事前規則としてp値・母集団CIは算出しない。二数値の追加には、情報の供給・目立ちやすさ・入力長の差が伴う。集計支援としての効果を測り、算術能力だけへの純粋な効果とは主張しない。

| 結果 | 今回の読み方と次の候補 |
|---|---|
| Pが増え、提案・全工程の両目安も達成 | この既知材料で集計支援が両立を助けた。未使用材料か次の更新巡へ |
| Pが増え提案目安達成、C/Jで失う | 提案側の支援効果と後続の境界を分けて報告。確認への情報供給・確認契約を次に検討 |
| 両条件とも高成績、差なし | 今回は合計追加の優位を確認しなかった。FC02との差を支援の効果に帰さない |
| 合計があってもP低迷 | 集計支援だけでは足りない。候補対応・旧記録との競合などを原因未同定の候補として残す |
| 本人判断・相手保持が崩れる | 共同の補助情報と個別判断の両立条件が未達 |
| 欠測で判定できない | 到達した工程と欠測理由を残して閉鎖 |

確認にも合計を見せる2×2比較は合計512生成になるため保留。提案は改善して確認で失われる場合に再検討する。最適候補をコードが決める方式、対案の再承認、新しい材料や計画的反復も別の候補として残す。
