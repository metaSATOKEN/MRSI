# CUSTOMER-UPDATE-01：変えるべき本人情報だけを変えられるか

2026-09-26／設計提案v0.1、略号CU01。第2報着手に向けた小診断。条件・分母・更新契約・終了条件を文書化した段階で、材料生成器、採点コード、プロンプト全文、Colab一セル版は次工程で固定する。実モデル生成0。

**担当客の希望が変わった人は更新し、相手は自分の担当客と共同の記録を守る。その後に古い通知が届いても、新しい希望を次の仕事に使えるか。**

## 1. 二つの例

| 初期状態 | 届く正当な変更通知 | 正しい最終状態 |
| --- | --- | --- |
| Aの客は犬、Bの客も犬 | Aの客は猫へ変更 | Aは猫、Bは犬。相手へ変更を波及させない |
| Aの客は犬、Bの客は猫 | Aの客は猫へ変更 | AもBも猫。本人ごとの正しい情報が、結果として一致する |

どちらもAだけが変更対象。両役に同じ通知を渡し、持ち主を見分ける必要を作る。紙／デジタルの共同観測には変更通知を出さず、共同の仕事は維持する。

「いつも違う犬猫を答える」は成功条件にしない。本人の事実に従って変わることと、別人の通知に引かれて変わることを区別する。

## 2. 材料と割付

新しい合成初期ノートを8組作る。**初期の希望が同じ／違う × 変更対象A／B × 変更対象の初期希望DOG／CAT** の2×2×2を全件使う。各組を新しい生成seedで2反復し、各反復で同じ初期状態から始める。

| 因子 | 各水準の材料数 |
| --- | ---: |
| 初期の希望：同じ／違う | 各4組 |
| 更新対象：A／B | 各4組 |
| 変更方向：犬→猫／猫→犬 | 各4組 |
| 共同案内：紙／デジタル | 各4組、試験中は固定 |

初期の希望が同じ4組では、変更後に違う希望になる。初期の希望が違う4組では、変更後に同じ希望になる。同じ場合の非対象役にも自分の現在値と異なる通知が届くため、犬猫の値だけでも巻き込みを検出できる。全組で人物・元ID・版も照合する。

SX02の保存物を改造して三巡目とは呼ばない。新しい更新契約を切り分ける診断である。新しいIDと場面ラベルを使うが、犬猫・紙／デジタルという課題族は既存のもの。

## 3. 担当客の更新契約

担当客の一行を `subject / animal / origin_id / revision` とする。`subject` は担当役AまたはB。`revision` は**その担当客の希望の版**であり、観測の版とは独立に扱う。

- ノートを持つ役と通知のsubjectが一致し、通知がその担当客の現在版より新しければ、希望・元ID・版を通知の一行へ更新する。
- 別の役の担当客通知では、自分の担当客欄を変えない。他人の版番号と自分の版番号を比較しない。
- 同じ担当客の古い通知では、現在の希望・元ID・版を維持する。
- 観測欄には、担当客通知の情報を書き込まない。

今回の通知は、実験側が正規の更新情報として与える。発行主体の真偽を認証する実験ではない。同版で内容が矛盾する通知、権限不明、担当交代は含めない。別人の通知を自分の更新根拠にしないことを評価する。

初期担当客の版と新しい希望・元IDは材料として事前固定する。希望更新は対象本人の初期版＋1、遅配はその本人の初期行そのもの。人物間の版の大小、通知の新しさ、観測の版を混同しないよう、担当客用の名前と領域を分ける。

**担当客欄はLLMに書かせ、正解への機械的な上書きをしない。** 意味の不一致は採点して残す。schemaはA/Bのいずれも受理する形とし、担当役を間違えた回答を構造欠測へ隠さない。

## 4. 一巡の流れ

| 工程 | 各役へ渡す入力 | 保存・点検すること |
| --- | --- | --- |
| CHANGE：新通知 | その役の初期ノート＋変更対象の新しい担当客通知 | 本人なら変更、相手なら保持。共同観測も保持 |
| DELAY：古い通知 | CHANGEで実保存した自分のノート＋変更対象の初期版通知 | 正しい更新から巻き戻らず、非対象を巻き込まない |
| READ：次の仕事 | DELAYの実保存ノートのみ | 自分のsubject・犬猫と、共同の四値を同時に使う |

各応答は新しいコンテキストで実行する。両役に同じ通知が届くが、二役間で保存物の交換は行わない。観測を実際に交換する継続系列はSX01・SX02で扱っており、今回は希望の更新境界に集中する。

CHANGE→DELAY→READは、その回の実保存物を読み戻して接続する。後続へ初期ノートや期待状態を差し戻さず、正しい通知を追加で再送しない。誤ったノートでも構造が成立すれば続行し、読出しで起きたことまで記録する。

観測保存には既存のG1P1（人物別最新版の一行複製）を用いる。ただし候補は**実入力ノートにある観測だけ**で、担当客通知は観測候補へ入れない。担当客用revision追加に対応するschemaとUPDATE指示を新設し、旧試験のschema・指示を上書きしない。

READはRU01／SX02のsubject・animal＋共同四値の形式を継承する。犬猫はLLM回答をそのまま使い、案内は回答された四値だけからコードで計算する。新しい担当客の元IDと版は保存時に採点し、READで再引用させる項目には追加しない。

## 5. 評価と予想

| 成分 | 判定 | 予定分母 |
| --- | --- | ---: |
| 本人の正当な変更 | CHANGEで対象役の担当客四欄が新通知に一致 | 16保存 |
| 相手の保持 | 非対象役の担当客四欄が初期と一致 | 32保存（CHANGE＋DELAY） |
| 古い通知への抵抗 | 対象役のDELAY保存が今回の正当な最新版と一致 | 16保存 |
| 本人・共同の観測保持 | 観測者・四値・元ID・版を含む全行が一致 | 64保存 |
| 後続利用 | 自分のsubject・犬猫、共同四値、実四値からの案内が正しい | 32回答 |
| **全工程成立** | A/B×3工程の6応答が全成立 | **16経路** |

保存前の原案と実保存後を分ける。各READは「渡されたノートへの忠実性」と「今回の正しい状態への一致」を別に評価する。DELAYで古い内容へ戻ったように見えても、CHANGEですでに更新に失敗していた場合は、新たな巻戻りと区別する。巻戻りはCHANGEが正しく成立した対象役を分母に、条件付き件数も示す。

仮説は、対象・版・保持範囲を明示した契約で、保持だけでなく正当な変更も接続すること。**全工程14/16以上、かつ各反復7/8以上**を小規模な実装上の目安とする。これは前系列と同じ種類の目安で、一般的な信頼性や統計的有意性の基準ではない。

- **MET：** 既知の成立だけで両条件を満たす。
- **NOT_MET：** 未確定をすべて成立としても、どちらかの条件に届かない。
- **INCONCLUSIVE：** 未確定の扱いで結論が変わる。

取得・構造欠測のある経路は主値を未確定とし、そこで既知の意味不一致があれば成分表へ残す。予定16を分母に欠測上下限を示す。初期の同異・更新対象・方向ごとの内訳と全件の成分を出し、総合値だけで巻き込みを隠さない。8設計ケースの記述的診断であり、二反復・役・工程を独立Nに足したp値や母集団CIは出さない。

## 6. 規模・予算・停止

**8組×2反復×2役×3工程＝最大96回答。** 更新64、READ32。最初の32入力を固定し、後続最大64入力を実保存物から組む。自動再生成0、準備込み45分、末尾90秒を終了処理へ確保する案。

固定Qwen/Qwen3.5-27B revision `fc05daec18b0a78c049392ed2e771dde82bdf654`、BF16・SDPA・non-thinking・batch1、temperature 0.7／top_p 0.8／top_k 20／repetition_penalty 1.0。入力8192・出力2048tokens、UPDATE原文16384・READ4096bytes、transformers 5.17.0／accelerate 1.15.0を継承する。既知の完全なJSONフェンスだけ除去し、内容を修復しない。

昨日のSX02では更新1件平均14.5秒、READ平均4.9秒だった。同じ速度なら今回の生成だけで約18分。環境準備・ロードを含む時間はGPUと接続状況に依存し、45分を上限にする。

Colab版は全文一セル、Driveなし、設定手編集・旧ZIPアップロード不要、終了ZIP自動ダウンロード。意味不成立でも続行し、保存不能は依存する後続だけ欠測。OOM・実行例外・時間上限は原記録を保存して閉じる。ローカルモデルロード0、既存Colab枠、新規購入・有料API0、非公開・削除期限なし。
