# 送信前と操作実行前に門番を置く案

2026-09-13。ユーザー提案は「生成時のツール呼び出し禁止の範囲を広げ、LLMに情報を回す前の受け口にも門番を置く」。**この方向を推奨する。** 今回は既存実装との照合と設計具体化まで。新部品の実装・モデル発行・実行経路への接続は行っていない。

## 何を補うか

既存のprepare_inline_generation (see the evidence index)は、信頼する割付側のhashとpacketを照合し、messageだけの厳格な形式を検査して本文を不変で取り出す。しかし、その後にホストが追加する指示・履歴・ツール定義を含む、最終送信要求を検査する部品ではない。hash一致も、その予定表自体の妥当性や実際のモデル到達を保証しない。

[直近の点検](tool-free-worker-results-2026-09-13.md)では、最上位tools欄を省略した要求でも、input.additional_toolsに3スキーマと入れ子のapply_patch宣言が残った。最上位だけの検査は不足だった。また[前回の実ホスト点検](runtime-capability-host-results-2026-09-13.md)では、通常hookは4操作を拒否できたが、終了コード1で壊れるhookの下ではtrueが実行された。両方の観測を設計の根拠にする。

## 1. 送信前の門番

本文を作った直後に加え、**すべての追加情報を組み立てた後、モデルへ送信する直前**に、決定論的な検査を置く。モデルへ本文を読むためのツールを使わせない。検査を通過した不変bytesを、そのまま送信器へ渡す。検査後にファイルを読み直したり、追加指示を足したりした要求には許可を流用しない。

| 検査対象 | 固定する契約 |
| --- | --- |
| 試行の所属 | run・trial・段階・モデル・許可された発行回数を、モデルが書き換えられない予定表へ結び付ける。二重発行を検出する |
| 履歴と本文 | 対象・時点・順序・発言者対応・全文hash・件数が予定と一致。他条件・未来・予定外の自己履歴を混ぜない |
| 盲検 | LLMへ渡す欄を許可リストで固定。研究仮説、条件名、他の採点、正解候補など、予定していない欄は送らない。管理用IDは外側の記録に置く |
| 最終要求の形式 | 明示した要求・message・contentの型と欄だけを許可。重複JSONキー、未知の型、余分な上位指示、継承conversation、予定外のtool resultを受け付けない |
| ツール提供 | 最上位toolsだけでなく、input.additional_tools・namespace・入れ子等、採用するプロトコルの全提供箇所を点検。未対応の表現形式を「ツール0」とみなさず停止 |
| 実際の送信 | 審査済み要求のhash・試行ID・発行状態を送信器側で確認。同じ要求が送信された記録を残す。adapterが後から情報を足す経路は不適合 |

ツール欄の省略と空配列の扱いは、採用プロトコルの全体を点検してから次カードで固定する。前回の結果を救うために遡って同一視しない。既存ホストが見えない場所で状態を足す場合、原本文の照合だけで「全文入力を制御できた」と認定しない。

## 2. 生成中の操作を実行前に止める門番

生成指示にも「許可する出力は指定形式の応答だけ、操作要求は禁止」と一貫して記す。その指示と別に、操作を扱うホスト側へ**すべて拒否を既定にする制約**を置く。ツール名をブラックリストへ追加し続ける方法にしない。

対象はshellだけでなく、patch・ファイル読取／書込・通信・browser・MCP・agent呼出し・待機や継続・入れ子の操作・将来追加された未知の操作を含む。通常応答テキスト以外の実行要求を認めず、応答内の文字列をプログラムとして評価しない。ツール定義を提供しない条件と、要求されても実行しない条件は別々に点検・記録する。後者の成功を前者の代用にしない。

門番の呼出しをLLMの判断に任せない。送信器・操作dispatcherが必ず通る位置へ接続する。例外、起動不能、timeout、検査結果の欠落、必要な監査記録の保存不能では、処理を送信・実行へ進めない。catchした後に通常経路へfallbackする実装は採用しない。現在のCodex hookだけでこの条件を満たせたとは扱わない。

## 研究内容を変えない境界

門番は入力の形式・出所・予定との一致・操作権限を検査する。P/Cの内容が妥当か、望む傾向が出そうかを判断して文章を削る・書き直す・差し替える処理は持たせない。必要な意味レビューは既存の測定工程で別に扱う。

本文中に「cat」「true」「tools」「前の指示を無視」などが登場しても、それが固定された研究材料の文章ならそのまま通す。操作の型・権限と、引用された文章を区別する。門番を検閲や本文修理へ広げると、履歴介入の条件そのものを変えてしまう。

異常時は原証拠と理由を保存し、INPUT_REJECTED／TOOL_REQUEST_BLOCKED／GATE_UNAVAILABLE等の経路状態として分ける。拒否後にエラー文をLLMへ返して続きを生成させることも、新しい入力介入になるため自動では行わない。その試行を打ち切るか、停止範囲をどこまで広げるか、再試行を許すかは実測前に固定する。過去の失敗回答をこの案で救済しない。

## 次の点検候補

まずネットワークもモデルも使わない合成fixtureで、正常入力・文章中のコード語句は無改変で通り、別条件履歴・未来情報・偽の上位指示・追加ツール・未知形式・二重発行は送信器／実行器へ到達しないことを確かめる。門番の例外・timeout・保存失敗でも到達0となることを、模擬の送信器と実行器の呼出し記録で点検する。単にvalidatorがエラーを返すだけのテストにしない。

その次に、選んだ実行経路で最終要求を捕捉できるか、門番を迂回できないかを合成小試験で確認する。ローカル部品の成功を実ホストの成功へ格上げしない。現行ログイン・Luna／Sol・費用条件を満たす接続先は未選定で、研究再走はまだ行わない。
