## 実装した境界

入口は、信頼する予定表のrun／trial／stage／model／最終要求hashに結び付けて検査する。今回制御するローカル形式は、model/input/tools/tool_choiceだけ。tools=[]、tool_choice=none、developer/userのmessageとinput_textだけを許可する。未知の欄や型、継承会話、tool result、入れ子のツール定義は拒否する。これはローカルの契約であり、CodexやAPIの送信形式との互換性を認定したものではない。

検査後に再構成せず、検査した同じbytesを模擬送信器へ渡す。SQLiteへ一意なclaimを先に保存し、送信直前にもCLAIMED状態と保存済み本文の完全一致を確認してSEND_INTENTへ進める。同じtrialは、並行呼出し・runner再作成・失敗後の本文差替えでも自動再発行しない。run全体を停止するcontrollerは未接続で、今回は各trialを一回限りにする部品の点検。

門番はローカルのPython子プロセス。監督側が終了コード・制限時間・応答形式・要求hash・予定への結び付け・一回限りchallengeを確認する。エラーを正常経路へfallbackしない。生成後は原返答を保存してから、type=textとtext文字列だけの形式を検査する。runnerには操作executorを配線せず、拒否通知をLLMへ返して生成を続ける処理も持たせていない。

## 点検で確認したこと

| 対象 | 最終版の観測 |
| --- | --- |
| 正常な犬猫の本文・空白・日本語・コードやJSONの引用 | 本文bytesと送信bytesが同一。管理IDの追加なし |
| 別条件・未来・発言者・順序・本文・上位指示・モデルの違い | 模擬送信0。予定hash／形式との不一致を拒否 |
| 追加情報・継承会話・未知型・重複キー・不正文字列・過大入力 | 模擬送信0 |
| 最上位tools・additional_tools・namespace・前回の捕捉要求 | 模擬送信0。既知の捕捉要求ではTOOL_DEFINITIONS_PRESENT |
| 二重発行 | 連続・並行・runner再作成後とも、一つのtrialの送信は最大1。失敗したtrialの再発行も拒否 |
| 門番の終了コード1・起動不能・不正／空応答・照合値違い・コード変更・timeout | 入力段階は模擬送信0。timeoutは返らない実際の子プロセスを打ち切った |
| 送信前の記録保存失敗、claim消失・本文変更・状態変更 | 模擬送信0 |
| 生成後のfunction/custom/入れ子/未知の操作、計15形式 | 正常入力の送信1後、操作実行0。原返答を保持 |
| ツール呼出しに見える引用を含むtext応答 | 文章を不変で受理し、コード評価なし |
| 送信器の例外・送信後の記録失敗 | 呼出し1と不確実性を保持。未送信と誤記録せず、再試行なし |

意味の良し悪しで本文を修理・選別する機能はない。hashによる照合は、信頼する予定表に対する一致の検査であり、予定表自体の時点・割付・盲検設計が正しいことの証明ではない。P/Cの測定や人格・NPPの認定も行っていない。

## 初回テスト後に見つけた不足と修正

初回は20テスト通過 (see the evidence index)、約8.285秒。その後のコード点検で、claimが途中で消失・変更しても、SQL更新の件数を確認せず送信へ進める不足を見つけた。元の合格ログ・コードを保持し、送信直前の状態／本文照合と、更新が必ず1件であることの確認を追加した。

最終の観測記録 (see the evidence index)は74行。再試行・並行処理の途中状態も含むため、74の独立標本や、行ごとの累積送信数の単純合計として扱わない。21テストのうち予定表の差替え拒否はunittestの例外検査で確認している。

実装をimportしない別実装照合 (see the evidence index)は492項目通過・失敗0 (see the evidence index)。原入出力と送信trap・操作trap、正常時のbytes一致、期待した拒否、旧版対照と修正版、固定ソース、旧3実験と関連部品の214ファイル不変を確認した。
