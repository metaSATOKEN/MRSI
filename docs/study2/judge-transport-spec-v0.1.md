# JUDGE-TRANSPORT-FIX：受理仕様 v0.1

2026-09-13。対象は採点の保存・構文・対応付け。意味の再定義やR1補修ではない。ローカル事前カード (see the evidence index)、[設計レビュー](formation-roadmap-review-2026-09-13.md)。

## 形式

入力はinstruction、current_event、itemsの3フィールド。itemsは匿名idとexplanationのみ。IDはi001等の`i`＋3桁、1〜999件を受理器の入力上限とする（実モデル試験の件数を承認する上限ではない）。explanationは空文字も許す。入力自体が不正なら判定用データにしない。

出力は次の4つの区切りと2欄だけ。コードフェンス・前置きは付けない。各ラベル行はID、半角スペース1個、許容ラベル。根拠欄は各IDについて3行で、QとRのコロン後には半角スペース1個。順序は自由だが、両欄とも全予定IDが各1回必要。

```text
BEGIN_LABELS
i001 P
END_LABELS
BEGIN_EVIDENCE
i001
Q: 参加者は犬の作品を好んで選んだ
R: 参加者の選好を行動の主因として採用している。
END_EVIDENCE
```

引用符・括弧・バックスラッシュは平文としてそのまま書ける。JSONの引用符閉じやエスケープを不要にする。Q／Rは各1物理行で、引用は入力explanationの連続した部分文字列。UNSCORABLEのみQの内容は空、Rは具体的な分類不能理由。改行コードはLF／CRLF、末尾改行1つの有無を許す。その他の正規化・空白除去・フェンス剥離・ラベル推測・修復はしない。

## 受理段階

1. receiptディレクトリを新規作成し、入力byte、出力byte、完了種別、hashを保存する。失敗出力も保存する。ファイル0600／ディレクトリ0700。既存receiptへの上書き不可。
2. 入力を厳密JSON（キー重複・NaN等を拒否）として検査。入力誤りはINPUT_ERROR。
3. completion_stateを確認。completed以外はINCOMPLETE／REFUSAL／INPUT_ERROR／MISSINGとして保存し、内容が正常形式でも有効登録しない。
4. ラベル票の構文、許容ラベル、IDの完全一致・各1回を検査。1件の異常でもラベル票全体を不成立とし、REJECTED_LABELS。
5. 根拠欄も予定ID完全一致・各1回、Q／R、引用一致、非空理由を検査。不成立ならLABELS_ONLY。正常なラベル票を診断用に残すが研究用のaccepted_ratingsは空。
6. 全て通過した場合だけACCEPTED_COMPLETEとして全予定評価を保存する。UNSCORABLEは出力契約として有効でも、解析用フレームはnull、stateはunscorable。OTHERやMIXEDへ変換しない。

構文上正常な理由が引用を意味的に支えているかは、この決定論的受理器では判断しない。ACCEPTED_COMPLETEは意味的正解の認定ではない。

診断ラベルを研究用の欠損へ代入する下流処理は作らない。受理結果の取得は入力・原出力・結果のhash照合と再計算一致を通す。ディスク上の改変を意図的に隠す攻撃への耐性を主張するものではない。

## 固定範囲

意味指示は旧プロンプト (see the evidence index)の冒頭から引用・理由要件の段落末までをbyte同一で取り出し、新しい出力形式の指示だけをその後へ足す。旧の出力JSON契約は置換し、旧ファイルは保持する。新しい形式制約が実際の判定を変えないとの主張はしない。

旧R1の5故障形、正常な引用符等、ID異常、途中終了、refusal、不正入力、保存失敗・改変検出を合成fixtureとI/O検査で点検する。正常を拒否した数と、不正を研究用に受理した数を別々に数える。検査fixture自体に期待値を持たせ、モデルに渡す入力には期待ラベルを入れない。
