## 2. 今回の懸念をどう整理するか

`own_experience_summary` だけを禁止文へ足し続ける方針では、名前や場所を変えた出力に追随する作業が増え得る。ただし、**OS01の既存schemaはもともと任意の追加キーを拒否する**。別名なら素通りする実装ではない。前回の一欄隔離は、既知答案を別枠で読むための監査用処理であり、一般的な受け口へ昇格していない。

次の契約は名前別の禁止から、次の不変条件へ重心を置く。

- 出力の形：その工程に許された欄と型だけを持つ。
- 帰属と参照：本人の根拠は本人の経験ID、共同の根拠は該当する共同記録IDへ結び付く。
- 本人判断：本人の経験から規則に従って選ぶ。共同の担当と一致する義務はない。
- 共同行為：資源制約と提案・確認の関係に従う。未承認の対案を合意済みにしない。

この課題の四条件は、構造化された入力と規則からコードで判定できる。**LLM judgeを足す必然性がすでに示された、とは結論しない。** 現段階では、機械で確認した事実を渡したjudgeが同じ境界を説明・点検できるか、正しい保留や本人と共同の違いを誤って違反扱いしないかを測るのが適切。

本当にコードの及ばない自由記述の帰属・言い換えを扱う段階では、別の意味課題と基準が必要になる。今回の64件は、その準備としての既知規則上の較正である。

## 3. 移植しないものとその理由

Meteonのjudgeは同一ローカルモデルの別役で、実装自身も独立採点者ではないと明記している。BJ01も同じQwenを新規コンテキストで使うため、その限界を引き継ぐ。多数決を真実へ置き換えない。

Meteonの「迷えばok」「例外時は元の挙動を維持」は、会話を誤切除しないための運用判断である。研究用のjudge出力では **UNRESOLVED／ERRORをOKと分ける**。機械が確定した違反をjudgeのOKで打ち消す権限は与えない。

また文字の包含率は計測値であり、それ自体が発言者や意味の完全な証明になるとは限らない。NPPへ数値閾値をそのまま移さず、元IDと役の対応・有理数による計算という、この課題で確定できる事実を使う。

次は[BJ01設計](../../experiments/BJ01/docs/boundary-judge-01-plan-v0.1-2026-09-28.md)。観測モードのjudgeを64件で点検し、その結果を踏まえて相手確認への共同計算支援へ戻る。既存答案の自動書換えや旧成績の更新は行わない。
