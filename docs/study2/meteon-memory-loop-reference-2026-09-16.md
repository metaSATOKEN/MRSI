## 2. 「再注入なし」の意味を明確にする

Meteonも、保存した記憶や要約をモデルの入力文脈へ戻している。したがって次の課題では、**研究者が毎回原票を再掲すること**と、**主体の仕組みが自分の保存記録を読み出すこと**を区別したい。

後者を許すなら、観測対象は「LLM＋個体に対応した保存先＋持ち越し・検索・提示の規則」である。履歴のない新しい呼出しへ何も渡さず、内部だけで覚えているはずだと扱う実験ではない。一方、原票を保存して毎回全文コピーするだけなら、それも一つの記憶装置ではあるが、経験からの選択・要約・更新まで検証したとは言えない。

初回の情報取得 → 保存記録 → 次時点への持ち越し → 取り出した記録 → 実際の入力 → 応答、という各段階を照合できる設計が参考になる。これにより、記録の脱落、検索漏れ、提示時の帰属混線、読めているのに判断へ使えないケースを分けられる。

## 3. 単体から群へ持ち込む際の境界

**記録を持つ主体、発言者、内容が指している相手は別である。** たとえばAが「Bは猫を希望していた」と覚える場合、記憶の持ち主はA、希望の持ち主はBになる。`persona`という話者欄だけで、この関係がすべて表現できるとはしない。NPPでは、個体の保存先、発言者・対象、時点、元記録ID、共有範囲を明示することが設計候補になる。

Meteonには会話sessionごとの保存に加え、orchestrator.py:149 (see the evidence index)とsleep_coordinator.py:147 (see the evidence index)で同じ固定scopeのDSTC状態を復元・保存する仕組みもある。単体の連続性を支える設計を、群全員に同じ保存先を与える形で写すと、検証したい個体間の境界が変わる。

また、ltm_search.py:29 (see the evidence index)の返却値は本文・persona・類似度・sourceで、保存metadata全体を構造化したまま返す形ではない。同ファイルの合流処理は本文で重複を除く。本文内のラベルは残り得るが、保存した全来歴が最後まで同じ欄で伝わるわけではない。NPPでは、保存時の正しい構造だけで帰属保持を合格にしない。

**類似記憶の統合と、正しい事実更新も別である。** memory_dynamics.py:318 (see the evidence index)の統合候補選択はベクトル類似度を使い、同一話者かを条件にはしていない。統合は既存のベクトル・強度等と統合元IDを更新し、既存raw_textやpersonaを新しい命題へ置き換える処理ではない。実際に誤帰属が起きたとの報告ではなく、この処理単体を「本人の記憶を正しく最新版にする装置」と見なせないという境界である。

## 4. 測定へ借りたいもの、分離したいもの

保持・自他分離・更新は、次のように別々に観測したい。

- **保持**：初回に得た本人情報が記録に残り、後続判断にも使えるか。保存と検索成功を別に数える。
- **自他分離**：他者の経験を参照・採用しても、誰の経験かを取り違えないか。他者の意見への同意だけを誤帰属としない。
- **更新**：変わっていない本人情報は保ち、変更された共通条件については判断を変えられるか。「変わらないほどよい」という単一得点にしない。

Meteonでは保存前の帰属センサーにlog-onlyの箇所があり、起床回答側には検知後の再生成・文の除去もある（sleep_processor.py:282 (see the evidence index)、direct_responders.py:396 (see the evidence index)）。それぞれの目的は異なる。NPPへ修正機構を入れるなら、初回応答・検知内容・修正後応答・修正コストを分け、修正後だけを「自発的に保持できた成績」としない。

またdeliberation_pipeline.py:1186 (see the evidence index)には、記憶encodeで採用されなかったターンも残すflight recorderがある。研究でも元の経験を独立に保存し、採用・検索・回答まで残った標本だけを見る選別を避けたい。
