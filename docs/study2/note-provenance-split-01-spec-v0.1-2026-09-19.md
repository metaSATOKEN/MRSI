# NOTE-PROVENANCE-SPLIT-01 — ノート本文・今回の参照・過去来歴を分ける

2026-09-19｜仕様草案 v0.1／限定オフライン点検完了。ユーザー承認：「読んだよー！！仕様整理賛成！やろうー！w」。研究モデル・認証・実送信0、既存取得器への組込み0。

## 先に、何を変えるのか

**ノートの内容を持ち越すたびに、その中の「読んだ資料名」を書き換える契約をやめ、今回の参照申告をノートの外へ出す。** 昔の記録は消さず、ローカルの履歴保管へ分ける。

たとえば、届いたノートの中に「昔はOBS_AとOBS_Bを参照した」と書かれていた。今回モデルが参照した記録名はINCOMING_GROUP。それなのに、コピーした本文のOBS_A/OBS_Bを「今回読んだ資料」の欄にも残してしまう。SR01では、この区別の不成立が保存16件中10件で観測された。

そこで、次へ渡すノートは「誰について何を記録したか」、今回の受領票は「今回どの記録を採用したと申告するか」、履歴保管は「元の文章に何が書いてあったか」を受け持つ。受領票はモデルの申告であり、実際の注意・推論過程を観測した証拠ではない。

## 変更の理由と固定しておく旧結果

[SHARED-RECENCY-01の結果](shared-recency-01-results-v0.1-2026-09-19.md)は、主E_PAIR=0/4、事前固定の内容感度=4/4。今回の仕様整理後も変更しない。

10件すべてで、出力した共同ノートが採用元の本文とJSON objectとして全文一致した。担当情報・観測値・版番号・元観測IDは正しく、現在参照欄だけが固定契約に違反した。昔の資料名は入力本文に実在するため、捏造とは断定しない。一方、現在入力の参照先として不適切だった事実は残す。内部のコピー機構が原因とまでは特定していない。

事前カード (see the evidence index)をコードより先に保存した。今回の既知例は不備10件だけでなく、旧基準成立6件を含む全16保存物。未見データ・独立標本・改善率の推定には使わない。

## 三つの保存場所

| 場所 | 保存するもの | 誰が作るか | 次のモデル入力に渡すか |
| --- | --- | --- | --- |
| `memory` | 個別ノート、共同ノート、共同版番号。人物・観測・案内・元観測ID | モデルの出力を検査後にそのまま保存 | 渡す |
| `read_receipt` | 今回採用した共同記録の名前。例：INCOMING_GROUP | モデルが申告。管理側は今回の入力hash・処理ID・参照先本文hashと結びつける | 本文には混ぜず、ローカルに保存 |
| `provenance_archive` | 旧入力全文、hash、そこにあった過去参照欄。旧出力原文も別に保存 | 管理側による決定論的な抽出・保存 | この試作では渡さない |

過去の申告は`LEGACY_NOT_RESOLVED`として保存する。古い名前だけでは、過去のどの処理のどの資料だったかを確定できない。古いOBS_A等を今のINCOMING_GROUPへ自動で変換せず、「旧本文で観測した申告」として保持する。

`origin_id`と`channel_origin_ids`は元の観測を識別するため本文に残す。ただしIDが残るだけで、その証拠の真実性や完全な来歴グラフが証明されるわけではない。

## 提案する入出力契約

出力の最上位は`memory`と`read_receipt`の2欄。`memory`は`private_note / shared_note / shared_revision`の3欄で、共同ノート内の`channel_read_refs`だけを廃止する。個別ノートと共同観測のA/B固定キーは維持する。

構造の概要（省略を含む説明用であり、このまま送るJSONではない）：

```text
memory
  private_note: 担当客 + 本人が観測した範囲 + 元観測ID
  shared_note: A/Bの観測 + 共同案内 + 元観測ID
  shared_revision: 1 / 2 / UNKNOWN
read_receipt
  shared_record_refs: [今回採用した共同記録名]
```

機械可読スキーマ (see the evidence index)。版番号1/2はSR01の既知例用の有限契約で、一般的な版管理の設計ではない。

入力の`scene / item / holder / records`は維持し、PRIVATEが1件、INCOMING_GROUPが1件、MEMORY_GROUPが0または1件。各共同記録は本文と版番号を持つ。管理側が提示した一覧を現在入力の登録簿とし、記録名の重複を拒否する。旧入力からの投影で削るのは、共同本文内の`channel_read_refs`のみ。削る前の原文と申告は保存する。

この試作の受領票は、**共同ノートを丸ごと1冊採用する操作の申告**である。すべての読んだ記録の一覧ではない。案内がPAPER/DIGITALなら共同参照ちょうど1件、UNKNOWNなら0件。今回のPRIVATEを共同採用元として書くことも拒否する。UNKNOWNを自動成功扱いせず、内容課題の採点で別に扱う。

### モデル向けの指示候補（未送信）

> 保存する内容はmemoryへ、今回採用した共同記録名はread_receipt.shared_record_refsへ書く。確定した共同案内を保存する場合、今回のrecordsにある共同記録を1件だけ申告する。共同案内をUNKNOWNとする場合は空配列にする。過去に参照された資料名や元観測IDを、今回の記録名の代わりに書かない。共同ノート本文に参照申告欄を追加しない。個別の担当情報、共同観測、元観測ID、版番号を、課題の規則に従って保存する。応答は指定されたJSONのみとする。

新旧の選択規則は個別実験の指示に属する。門番はその正解を埋めない。この指示は実測していないため、従えるかは未確認。

## 門番がすること・モデルの判断として測ること

| 層 | 確認 | 不成立の扱い |
| --- | --- | --- |
| 入力検査 | 閉じたキー、記録名の一意性、PRIVATE/共同の区分、型・本文構造 | 管理側の入力不備として送信前に止める。モデル失敗に数えない |
| 出力の形式と参照 | 最大4096 byte、重複JSONキーなし、型・必須欄・余分欄、参照数、参照名が今ある共同記録か | 原文と形式が成立する部分を保存し、依存する次処理への引継ぎを止める |
| 局所整合性 | 個別本文がPRIVATEに一致するか。共同本文・版が申告した記録に一致するか | 別欄へ観測値として記録。自動修理しない。これは今回の門番の合否には足さない |
| 研究上の成績 | 課題上正しい資料・内容を選んだか。本人の情報を保ったか。次の仕事で使えたか | 次実験で事前固定した基準により評価 |

参照先が実在するだけでは、資料選択の正しさは保証できない。**実在する古い版の本文・版番号を忠実に保存した例は、門番も局所整合性も通る。** それでも「最新版を使う」課題なら不正解である。この反例を人工例として保存した。

局所整合性は、この試作ではJSON objectの完全一致を使う。集合として同じでも配列順序が異なる場合は一致にならない。旧実験の集合相当の比較器を変更したわけではなく、これを将来の意味採点にそのまま流用しない。

管理側はモデルが申告した別名を、`処理ID + 現在入力hash + 記録名 + 参照先本文hash`へ結びつける。同じINCOMING_GROUPでも処理が違えば別記録として扱う。この結びつけは申告の所在を明確にするもので、モデルが本当にその記録を根拠に推論した証明にはしない。

欠測・nullの推測補完、余分欄の除去、人物・値・版の訂正、意味修復リトライはこの試作にない。原文の旧出力を新書式へ変換して成功へ上げる関数も作らない。

**停止規則は将来の変更候補。** SR01では構造成立・意味不備の保存物はそのまま継承した。提案では現在参照の不成立でも依存する引継ぎを止める。そのため、将来の実験では「門番拒否」「後続未発行」「観測された誤答」「UNKNOWN」を分け、固定分母と停止規則を先に定義する。SR01へ遡及適用しない。

## ここで閉じて、次に進む条件

今回の終点は仕様と有限なオフライン点検。LLMがこの書式を守れるか、受領票分離が誤りを減らすかは未測定。入力から過去参照を外すこと、出力配置を変えること、門番を追加することが同時に変わるため、後の成績差を「欄を分けた効果」だけに帰属しない。

**推奨する次工程は、この分離を土台に、二人が別々に更新した情報を持ち寄る小試験の設計へ戻ること。** 相手の新しい情報を受け取りつつ、自分だけが持つ新しい情報を古い相手ノートで上書きしないかを測る。「個別に持つ情報」と「群で使う状態」の両立へ戻る。

ただし、今回の試作は共同ノート1冊を選ぶ契約であり、二つの観測を統合する操作にはそのまま使えない。次の設計で、どの欄を誰が更新できるか、二つの出典をどの粒度で申告するか、別々の更新番号を比較できるかを先に決める。機械が新しい値を自動合成して正解を作らないことは維持する。

| 選択肢 | 方針・コスト・再検討条件 |
| --- | --- |
| **二人の別々の更新を持ち寄る小設計** | 推奨。今回は設計前で実送信0。本人情報と共同更新が衝突する具体的な失敗を小規模で観測できる。要求数・採点・停止規則を先に固定する |
