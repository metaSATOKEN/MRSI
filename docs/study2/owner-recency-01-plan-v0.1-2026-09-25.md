# OWNER-RECENCY-01：誰の最新版を、どこまで機械で守るか

2026-09-25／設計v0.1。材料・指示・保存処理・採点・割付を固定し、オフライン点検まで完了。実モデルの生成は次工程。

**同じ更新案から4通りのノートを作り、「共同ノートだけを守る」「本人の観測も守る」の違いを調べる。** JSONの外装は全条件共通の受け口で整える。

前回の[別枠点検](update-readout-01-envelope-reference-2026-09-25.md)では、72更新中51件が完全一致し、21件には古い共同観測が残った。そのうち3件では本人の観測も壊れ、1件は相手の観測が本人欄へ入っていた。今回は、この二つの保存先に処理を置く範囲を比べる。

## 1. 比べる4通り

各材料・反復につき、LLMがまず一つの更新案を書く。その**同じ案**から次の4条件へ分岐する。

| 条件 | 共同ノートのA/B行 | 本人ノートの観測欄 | 見たいこと |
| --- | --- | --- | --- |
| G0P0：モデルの案を保存 | そのまま | そのまま | 今回の基準 |
| G1P0：共同だけ固定 | 人物別の最新版を複製 | そのまま | 共同状態を整えると、どこまで成立するか |
| G0P1：本人だけ固定 | そのまま | 本人の最新版を複製 | 本人欄を守っても、共同状態の不備が残るか |
| G1P1：両方を固定 | 人物別の最新版を複製 | 本人の最新版を複製 | 未処理欄・後続の読出しに何が残るか |

「固定」は、古い情報を永久に保持する意味ではない。**入力にある候補から、対象の人物の最新行を選び直す**処理を指す。

どの条件でも、担当客の犬猫希望・人物・出典（customer）はLLMの案を保持する。本人側で機械化する範囲は観測欄（coverage）。この切り分けで、機械に任せた欄とモデルが書く欄の両方を点検する。

二つの比較軸は「共同側を処理するか」「本人側を処理するか」。所有者の絞込みと版の比較は一つの部品として使う。その二操作の単独効果まで知る必要が生じた場合は、次の比較に分ける。

## 2. 機械に任せる処理

処理は次の順に固定する。

1. 共同A欄ならobserver=A、共同B欄ならobserver=B、本人欄ならobserver=holderに候補を絞る。
2. **その人物の候補の中だけで**数値revisionを比較し、最大の行を選ぶ。
3. 人物・紙／デジタルの観測値・版・出典IDを、行全体で複製する。

Aのrevision 3とBのrevision 4を比べて、Bだけを採る処理にはしない。通知の到着順も使わない。

元資料と候補一覧の内容対応を検査する。同人物・同版で内容が一致する重複は候補位置ID順の先頭を使い、選べた重複候補をすべて履歴へ残す。同人物・同版の内容が矛盾する、必要な人物がいない、候補が元資料と一致しない場合は、当該更新案の全分岐を契約エラーとして保留する。残りの独立材料は処理する。

保存器に渡すのは**実際の更新案・元の入力資料・条件指定**。正解データを渡さず、どの候補を複製したか、処理前後の行のhash、実際に変わったかを保存する。

今回の資料は、人物ラベルと版番号が正しく、最新行が入力内にあり、同版の矛盾がない契約で作られている。この下で機械処理した行が正しくなることは、コードの性質として点検できる。実験で見たいのは、**その処理を置いた後、本人情報と共同状態を一緒に保存でき、次の判断まで使えるか**である。

## 3. JSONの既知問題は共通の受け口で整える

前回37実回答で確認したコードフェンスを、自動除去の対象として取得前に固定する。点検済みadapter (see the evidence index)を、今回のUPDATEとREADの両方へ適用する。

| 入力 | 処理 |
| --- | --- |
| そのままで読めるstrict JSON | 元のバイト列を保持 |
| 先頭が```json＋改行、末尾が改行＋```の一つの囲い | 外側12バイトだけ除去し、内側全文を再検査 |
| 内部の括弧不備、重複キー、必須欄欠落、別形式の囲い等 | 理由付きで形式不成立として記録 |

原文、正規化後の文、適用規則、前後hash、除去量を別々に残す。人物・値・版・IDの変更は、このパーサーの仕事に含めない。保存介入による行の置換は、別の処理履歴として記録する。

EOSで終わった応答だけを対象にし、原文の上限はUPDATE 16,384バイト／READ 4,096バイト。コードフェンスを除けば短くなる場合も原文上限を適用する。補正前の形式成立数と補正後の成立数を併記するため、形式の負担も見える。

Meteonから借りるのは、**正常なJSONを先に読み、安全性が確認できた修理を後段へ置く**という順序。JSONパーサーの注意書き (see the evidence index)と鉤括弧を含む正常文字列の回帰例 (see the evidence index)を静的に再確認した。Meteonの欠落補完や既定値投入は用途が異なるため、今回の計測用パーサーには持ち込まない。新たな形式不備が出たら実例を保存し、安全な修理規則と境界テストを追加する次版の候補にする。

## 4. 材料と規模

UR01で使用した18材料を**全件そのまま**再利用する。今回のために成功例・失敗例を選び直さない。

| 集合 | 状況 | 材料 | 反復後の各条件の分母 |
| --- | --- | ---: | ---: |
| 修復 | 古い共同行に対し、最新通知が届く | 10 | 20 |
| 巻戻り防止 | 最新状態に対し、古い通知が遅れて届く | 8 | 16 |

修復側は保持役A1・B9、通知本人1・相手9という元の偏りを保持。巻戻り側は保持役A/B、通知本人／相手、最新案内の紙／デジタルが各4対4。独立材料は18で、二反復・四分岐を独立Nへ足さない。

**元の本人観測は18材料すべて最新版。** したがって本人側の主な点検は、更新中の巻戻りと相手行の混入を防げるか。本人に新しい観測が届いて更新する課題は、次の材料候補として残す。

今回は新しい更新案36件を取得する。旧UR01回答の修正や、前回未実施だったREADの穴埋めではない。旧正式成績と参考成績はそのまま保持する。

## 5. 後続の読出しと重複生成の節約

各分岐で実際に保存した個別・共同ノートを、次の新規コンテキストへ渡す。READは従来と同じ指示・schemaで、共同A/Bの紙・デジタル四値を抽出する。その実回答だけから、固定コードで案内方法を計算する。通知・候補一覧・正解・分岐名は再掲しない。

**同じ更新案からできた分岐で、READ入力が完全に同じなら一度だけ生成して共用する。** 同一性はmessages・schema・モデル設定・seedの完全一致で、回答を見る前に判定する。違う個別ノートが入っていれば、共同ノートが同じでも別入力として読む。別材料や別反復の間では共用しない。

共用元の応答IDと各分岐の対応を保存し、「144分岐を評価した」と「144回生成した」を分ける。同じ入力の偶然の応答差を介入効果へ混ぜず、重複する生成も減らす設計である。二反復では別seedを使う。

読出しが直接測るのは共同四値と案内判断。本人情報の成否は保存段階で点検する。本人観測の出典を後続で再引用する能力は、このREADには含めない。

## 6. 指標と比較の読み方

| 段階 | 数えること |
| --- | --- |
| 共通更新案 | 裸JSON／囲い除去／不成立、各欄の不備 |
| 保存後 | 担当客保持、本人観測の人物・版・行全体、共同A/Bの人物・版・行全体、全欄完全一致 |
| READ | 実保存四値への忠実性、最新状態に対応する案内 |
| 全工程 | 保存全欄＋READ四値＋最新案内がすべて一致 |

形式・契約・依存欠測は未確定として残し、予定分母で一致／不一致／未確定を表示する。READが欠けても、既に分かった保存不備は別の成分成績へ残る。全工程指標は両工程の構造成立を前提とする。

共同側の差は「G1P0−G0P0」と「G1P1−G0P1」、本人側の差は「G0P1−G0P0」と「G1P1−G1P0」。修復／巻戻り防止、反復、材料ごとに、改善・悪化・同じ・未確定を並べる。欠測がある場合は差の取り得る上下限も示す。

**比較元に本人欄の不備が出なければ、「今回は防ぐ機会を観測しなかった」と報告する。** 差ゼロを、本人側の処理が不要という結論へ置き換えない。材料が既知で、機械が処理する欄は構成上守られるため、p値や母集団信頼区間は算出しない。

次工程への記述的目安は従来に揃える。各条件で、修復18/20以上・各反復9/10以上、巻戻り防止14/16以上・各反復7/8以上、担当客36/36。保存全欄と全工程を別々に判定する。

- **MET**：既知の一致だけで目安に届く。
- **NOT_MET**：未確定をすべて一致としても届かない。
- **INCONCLUSIVE**：未確定の扱いで判定が変わる。

これは構成を次へ進める工学的目安。統計的有意差の基準ではない。

## 7. 実行条件と上限

| 項目 | 固定内容 |
| --- | --- |
| モデル | Qwen/Qwen3.5-27B、revision `fc05daec18b0a78c049392ed2e771dde82bdf654` |
| 生成 | BF16・SDPA・non-thinking・batch 1、temperature 0.7、top_p 0.8、top_k 20、repetition_penalty 1.0、samplingあり |
| 長さ | 入力最大8,192tokens、出力最大2,048tokens／生成 |
| 環境pins | transformers 5.17.0、accelerate 1.15.0 |
| 更新 | 18材料×2反復＝36生成 |
| READ | 最大144生成。親内の同一入力だけ共用 |
| 合計上限 | **180実生成、準備込み90分、自動再生成0** |
| 実行先 | ユーザーのColab GPU。一セル、Drive接続なし、最終ZIP自動DL |
| 保管 | 非公開、削除期限なし。追加API支払い0 |

全親が構造成立し、4分岐がすべて同一なら36更新＋36READ＝72生成。すべて異なれば180生成。実際の件数と所要時間は返送ZIPで確認する。90分は停止上限であり実行時間の予測ではない。

更新の形式不成立は、その親の4READだけを依存欠測にする。意味不成立でも保存できればREADへ渡し、独立材料は続行する。時間上限・実行例外は原回答と到達点を保存して閉じる。自動で延長・再送しない。途中ZIP、再クリック時の重複防止等は次の接続準備で結線・検証する。

UPDATE指示はUR01 REWRITEを基礎に、今回存在しない方式比較への言及「両方式とも」の5文字だけを除去した。UPDATE schema、READ指示・schema、モデル設定は前回と同じ。モデルには後段の4分岐を知らせず、一つの更新案を書かせる。

## 8. 結果を受けてどこへ進むか

固定した一巡で閉じる。

| 結果 | 次に判断すること |
| --- | --- |
| 両方を固定して全工程が目安へ到達 | 新しい材料で本人更新・共同更新・交換へ進める構成候補になる |
| 共同だけでも到達し、本人の不備機会が観測された | 本人側を加えた時の対応差を使い、追加処理の必要範囲を検討する |
| 本人欄の不備が全く出ない | 本人側の効果は未識別。次に本人の新通知を含む材料を検討する |
| 両方を固定しても未達 | customer記述、受け口、後続読出しの残存不備を一度診断する |

新材料の大規模追試、所有者と版比較の別要因化、同版矛盾、本人出典の後続利用は候補棚へ残す。今回の結果を見ながら条件や反復を増やさない。
