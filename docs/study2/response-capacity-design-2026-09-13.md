# 原SSEの容量設計 — JUDGE-BOUNDARY-01の停止を受けて

2026-09-13。オフラインの修正設計案。コード改訂・新規モデル実測は未実施。元の[未成立結果](judge-boundary-model-results-2026-09-13.md)とsender v2／gate v2を保存する。

## 推奨する範囲

入力／認証bootstrapの上限256 KiBを維持し、**出力の原SSE上限を4 MiBに分離**する。復元した最終本文はUTF-8で64 KiB以下と別に制限する。この数値は今回の部分観測から選ぶ候補上限であり、16例が必ず完了するという推定ではない。最大受信量・保存量・門番への転送量を明記し、上限をなくさない。

4 MiBのSSEに対して、1イベント／JSON frameは既存の256 KiBを維持する。イベント数は最大20,000。4 MiB・イベント数・復元本文64 KiBのどれかを超えたら放出しない。時間上限は既存の受信120秒／CLI180秒を維持し、プロセス全体の範囲は新しいカードで固定する。

今回の例では、16例を小分けにすると、採点時に同居する説明や要求数が変わる。採点指示を短くする、全文引用を禁じる方法も測定条件を変える。まず輸送容量だけの変更を試す方が、固定した16例・同一packet・同じ意味基準を保てる。

## 変更が必要な場所

- senderのHTTP読取量を出力専用上限へ結び付ける。残量＋1 byteを超えて読み込まないようにし、超過時の診断保存も上限＋1までと明記する。例外前にHTTPステータス・header名等の非秘密メタデータを保存し、失敗理由をRESPONSE_SIZE_LIMIT／READ_DEADLINE等へ分ける。認証値の反射検査は部分保存にも適用する。
- wire gateの原SSE上限、イベント数、復元本文上限を同じ出力契約へ合わせる。gate子プロセスへ渡すbase64 envelopeにも有限の明示上限を設定する。入力のstrict parserを一括で4 MiBへ緩めず、用途ごとに分離する。
- 元のSQLite claim→送信予定照合→原保存→出力gate→本文放出の順を維持する。未知event、操作item、ID／連番／delta／doneの不整合、欠落完了を引き続き拒否。部分本文から完了を合成しない。
- sender・gate・envelopeの上限がずれていれば、実発行前の局所点検で止める。新しい上限とコードhashを別版で凍結する。

## 実装後に必要な局所点検

ネットワーク外向き通信・モデル要求0で、合成HTTP/SSEを使って次を検証する。

1. 原SSEが256 KiB以下の従来正常例と、256 KiB超〜4 MiB以内の長い正常例が、同じ原文bytesで最後まで受理される。
2. 上限ちょうどと上限＋1 byte、イベント数の上限／超過、復元本文64 KiBの上限／超過を対で点検する。chunk境界で上限を越えても、保存量を宣言範囲内に保ち、本文放出0。
3. 長いstream中の操作要求、未知型、重複／不一致、途中切断、完了欠落を拒否。今回の既知部分SSEもサイズ以外の未完了条件で拒否され続けることを確認する。
4. gate envelopeの新上限、門番の異常終了／timeout、記録保存失敗、同ID再発行拒否を確認する。許可する内容が増えたと誤解しないよう、正常長文と不正長文を対にする。

完了したライブ応答の必要サイズは今回未観測なので、局所通過を16例の取得成功とは呼ばない。局所点検を完了後、新規モデル試験の件数・時間・保持条件を提示する。既知部分票は再採点や成功票の代用に使わず、16例は今回すでにモデルへ提示した既知fixtureとして扱う。新しい再試行を未見標本と呼ばない。
