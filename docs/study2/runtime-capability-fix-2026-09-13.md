# 操作を実行前に制限する：RUNTIME-CAPABILITY-FIX-LOCAL-01

2026-09-13。**推奨は、固定本文を直接渡し、研究用LLMが使える操作ツールを0にする構成。** 操作要求が出た場合は、実行側で拒否する。今回の提案に沿ってローカル部品を試作し、13テスト通過・失敗0。実ホストへは未接続で、状態は `PASS_LOCAL_COMPONENT / HOST_ENFORCEMENT_UNVERIFIED`。

## 今回の問題の所在

MEMORY-OWNER-01には既に、入力hash・JSON形式・予定ID・引用・操作ログを検査する決定論的処理があった。しかし、操作の検査は**実行後のログ監査**だった。16セッションの可視17呼出しは16回のcatと1回のtrue。trueを止める機構が実行前にはなく、終了後に経路不成立とされた。[旧結果](memory-owner-results-2026-09-13.md)、今回読んだ操作数 (see the evidence index)。

したがって、新しい検査をプロンプトで「必ず呼べ」と追加するだけでは不十分。モデルが通らずに済む経路を残さず、ホストが実行前に適用する必要がある。前回の「無害な追加操作を失格にしない」案よりも、まず操作の必要性と実行権限を取り除く方向を優先する。過去の停止条件を遡って緩めたり、旧16回答を成功扱いに変更したりはしない。

## 制約を置く3箇所

1. **入力の準備**：主プロセスが割付と入力hashを照合し、全文を直接渡す。workerにファイル名やshellを渡す必要をなくす。`prepare_inline_generation`は本文・空白・順序を変更せず返す。hash一致は意味を理解した証明でも、モデルへの到達の証明でもないため、実送信の記録は別に必要。
2. **実行権限**：研究用workerのツール一覧を空にする接続を第一候補とする。追加の防御として、操作要求が到達したら実行前にdenyする。入力本文に「true」「cat」が現れても操作とは扱わない。出力文字列をコードとして評価しない。
3. **出力の受理**：既存の生成JSON／採点ID・引用検査を継承し、rawを保存した上で受理を決める。不正な出力を自動修正・再採点して埋めない。構文制約はP/Cの意味的な正しさを保証しない。

## 現在使える接続点と限界

現在露出している `collaboration.spawn_agent` の引数には、個別workerのツールを空にする設定はない。本文を直接渡す変更だけでは権限は消えない。

OpenAI公式仕様では、CodexのPreToolUseは入れ子のexec_commandも実行前に拒否できる。一方、hosted toolなど対象外の経路があり、hookだけを完全な権限境界とはしない。子のhookではsession_idに親IDが入るため、親IDだけでworkerを識別する設計も避ける。[OpenAI Docs：Hooks](https://learn.chatgpt.com/docs/hooks)。ローカルCLIは `0.154.0-alpha.6.2`、読み取り用のfeature一覧ではhooks=true。ただしデスクトップの当該workerへ適用済みという証拠ではない。

別の管理下runnerへ移る場合、APIの `tool_choice: "none"` とツールを渡さない構成が候補になる。[公式Function calling](https://developers.openai.com/api/docs/guides/function-calling)。今回はAPIへの移行・認証設定・呼出し・課金をしていない。現行モデル／利用枠での接続方法は別途確認が必要。

## 次に実機点検する条件

次は研究本文を使わない専用workerで、(a)親とworkerを区別できる、(b)生成に不要なツールを非公開にできる、(c)true・別ファイル・通信・書込が実行前に遮断される、(d)未知経路やゲート故障時に処理が通らない、(e)遮断履歴を保存できる、を確認する。対象経路を網羅できなければ、完全な封鎖とは報告せず接続方式を変更する。
