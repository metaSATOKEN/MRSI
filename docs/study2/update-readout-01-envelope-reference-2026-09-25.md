# UR01参考分析：外側の囲いを除くと、37件中27件の更新内容が一致

2026-09-25。ユーザー承認に基づき、JSONの外側のコードブロックだけを除く処理を点検し、正式受理35件と合わせて更新72件を再評価した。**形式で止まった37件は全件構造検査を通り、内容まで完全一致したのは27件。残る10件には意味上の不備があった。**

この別枠の合算で、修復の完全一致はREWRITE12/20・SELECT13/20、巻戻り防止は11/16・15/16となった。形式の問題を除いても、最新版を採る工程に課題が残ることが分かった。

本書は**取得後に行った更新内容の参考分析**。[正式報告](../../experiments/UR01/docs/update-readout-01-result-2026-09-25.md)、原回答、本番セル、実験時の保存物は保持した。新たなLLM生成は0。未実施のREAD37件は欠測のまま残している。

## 1. 何を正規化したか

対象は更新の全72原回答。同じ処理を一律に適用し、裸JSONの35件はbyte不変、囲い付き37件は先頭8バイトと末尾4バイト、計12バイトだけを取り除いた。合計444バイトの除去となる。

~~~text
除去する先頭：```json + LF
保持する部分：内側の全文、そのまま
除去する末尾：LF + ```
~~~

処理はEOS・UTF-8・原文16384bytes以内を前提とする。前置き・後書き、複数のJSONやブロック、別ラベル・別改行形式、括弧不備、重複キー、NaN等は拒否する。空白・キー・値・人物・出典・版を変更せず、欠落を補わない。schema検査、候補位置の解決、意味採点は凍結済みのコードを使用した。

**15件の境界テストが初回通過。** JSON内の文字列を変えないこと、二度目の処理が無変更になること、誤出典・旧行選択が正解へ変換されないこと、実72原回答のbyte対応を点検した。派生フォルダには原文・正規化文・両hash・除去量・参考採点を保存した。SELECTの再構成も、実際の選択位置から原行を複製している。

表の「一致」は、担当客・本人観測・共同A/B行の人物／値／版／出典がすべて期待する更新状態と一致した件数。後続READの成績は含まない。

囲い付き37件だけでは27一致・10不一致。元の受理35件は24一致・11不一致で、その評価は変わらない。合算は51一致・21不一致・未確定0、内訳はREWRITE23/36・SELECT28/36となる。この合計は記録の収支であり、修復と維持を混ぜた方式優越性の指標にはしない。

反復別の更新完全一致も確認した。

| 方式 | 修復・反復1 | 修復・反復2 | 維持・反復1 | 維持・反復2 |

取得前の数値目安を参考値へ当てはめても、修復18/20に届かず両方式ともNOT_MET。SELECTの維持は14/16・各反復7/8の目安を満たした。方式差の記述的改善信号は、修復の差＋4/20以上と両反復の正差を満たさず成立しない。逆方向も成立しない。独立材料は18、各二反復であり、p値・母集団信頼区間は算出していない。

## 3. 形式で隠れていた本人観測の不備

| 更新内容の成分 | REWRITE | SELECT | 合計 |
| --- | ---: | ---: | ---: |
| 担当客の人物・犬猫・出典の保持 | 36/36 | 36/36 | **72/72** |
| 本人観測の人物・値・版・出典の保持 | 33/36 | 36/36 | **69/72** |
| 共同A/B行が両方とも最新 | 23/36 | 28/36 | **51/72** |

共同144行はすべて入力に存在する行と完全一致していた。うち123行が最新、21行が古い行だった。共同欄の不備は修復で旧行を残した15件、遅配された旧通知を採用した6件。REWRITEで見つかった本人観測の不備3件は、この巻戻り6件の一部に重なるため、合計して24系列とは数えない。

本人観測の3件はいずれも、囲いで未確定だったREWRITEの巻戻り防止条件から見つかった。

- **`UR01-G04`の反復1・2：本人の古い通知へ巻戻り。** 保持役Bの本人観測はrevision 4だったが、遅れて届いた本人のrevision 1が個別欄にも共同B欄にも書かれていた。
- **`UR01-G06`の反復2：相手の古い通知が本人欄へ混入。** 保持役はAなのに、個別ノートの観測欄へ相手Bのrevision 1が入っていた。共同B欄も同じ旧通知へ巻き戻った。担当客のAという人物・希望・出典は保持されていた。

後者は、担当客の情報を保つことと、観測を誰のものとして保存するかが別の点検対象になる事例である。この回答ではREADを実施していないため、ここで確認したのは原回答の内容と事後再構成まで。

## 4. 合算できる範囲と、残した欠測

今回72件へ合算できたのはUPDATEの内容評価。新しく評価可能になった37件から、実験時に保存・読出しが行われたことにはしない。再構成物には `POSTHOC_RECONSTRUCTION_NOT_EXPERIMENT_SAVED_MEMORY` と明記した。

実際に行ったREADは元の35件で、四値抽出35/35・最新案内25/35のまま。後続までの完全一致も正式評価と同じで、REWRITEは6一致・5不一致・25未確定、SELECTは18一致・6不一致・12未確定を保持した。

参考として、再構成した共同ノートの四値から案内を**機械計算**すると、最新案内への一致はREWRITE24/36・SELECT29/36、計53/72となる。これは「そのノートの値を忠実に読んだ場合に、規則が返す案内」であり、72件のLLM読出し成績ではない。

更新の完全一致51/72より、この静的案内一致は2件多い。1件は既に実測した `UR01-G03-R1-SELECT`、もう1件は今回見つかった `UR01-G06-R2-REWRITE`。G06では本人観測の取り違えと共同欄の巻戻りがあっても、共同四値の機械計算だけならDIGITALが合う。こちらを「後続が正答した事例」とは数えず、文面だけでは見落とし得る不備の説明に使う。

## 5. 今回の結論と次の指針

**37件中27件は、更新内容が合っていても外装で止まっていた。** 一方、残り10件は囲いを外しても内容不備が残った。この別枠点検によって、形式の問題で見えなくなっていた更新内容を評価できた。

全件を見た修復成績は12/20対13/20で、主な残課題は最新版の採用にある。巻戻り防止では11/16対15/16という記述的差があり、REWRITEの本人観測欄には巻戻り2件と相手観測の混入1件も見つかった。

次の小設計では、**「誰の行かを先に固定し、その人の最新版を選ぶ」処理をどこまで決定論的に担わせるか**を検討するのがよさそう。共同欄の最新版選択と、個別欄へ入れてよい観測者の制約を分けて比べれば、今回の旧行保持・巻戻り・本人欄への混入をそれぞれ追える。外装の受け口は今回の点検済み部品を候補にできる。

本番セルへの組込みと新たなLLM実験は次設計で決める。今回は依頼された正規化点検・別枠合算・照合・記帳までで閉じた。
