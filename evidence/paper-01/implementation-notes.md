## 付録C. 実装上の工夫と保証の境界

本付録は、結果を支えた実装を「何をモデルに任せ、何をプログラムで固定したか」から説明する。C.1〜C.7は主にRC01・RC02の取得時コードを対象とし、SC03の書式変換は別に示す。追加二実験の撤回状態・中断継続・派生解析をC.8〜C.10に記す。後半の実装を、初期試験にもすべて備わっていたものとして遡及しない。以下のコードは説明用の抜粋・疑似コードであり、完全な実装への入口は末尾に示す。

### C.1 出力の契約を、指示と検証器で共有する

共同観測は、配列の順番から役を推測する形式を避け、`coverage.A`と`coverage.B`の固定キーを持つobjectで表した。観測者、紙・デジタルの値、元ID、後半では版番号を必須欄とし、追加キーや型の暗黙変換を許さない。schemaを生成する関数の返り値を、モデルに示す指示と受領後の検証に使う。これは生成結果が必ずschemaに従う保証ではなく、期待する形と受け口のずれを減らす実装である。

JSONの読取りでは、重複キーを「後の値で上書き」せず拒否する。非JSON数値、過大な出力、必須欄の欠落等も検出する。RC02の本文上限は4,096 UTF-8 bytesであり、切詰めて成功扱いにはしない。検証器はこの課題で使う有限のschema語彙に対応するもので、汎用のJSON Schema実装とはしていない。

SC03には、明示された観測者A/Bが各一件ある二件配列に限り、観測行の中身を変更せずA/B objectへ並べ直すcodecを用いた。配列の位置から人物を推測したり、欠けた行・値を補ったりしない。変換先を一意に決められない配列は拒否する。

| codecの状態 | 処理 | 保存する証拠 |
| --- | --- | --- |
| NATIVE | 元から契約に適合。原文bytesをそのまま受理 | 原文・受理文のhash |
| NORMALIZED | 明示observerに従って配列をobjectへ変換 | 原文と派生文、変換規則、変更箇所、行の対応 |
| REJECTED | 曖昧・欠落・余分な欄等があり受理しない | 原文と拒否理由。受理文は生成しない |

既にobject形式なら、A欄にBの観測が書かれていても、型が適合する限り人物を入れ替えて直すことはしない。構造の変換と内容の正否を分けるためである。SC03の実出力8件はすべてNATIVEだったので、NORMALIZEDの経路は合成・既知例のオフライン確認にとどまる。schemaを指示へ載せる方式であり、生成時のStructured Outputやgrammar制約による強制を実測したものではない。[codec実装](references/scripts/shared_note_codec_v1.py)（原コード行119）

### C.2 門番を通ることと、正しいことを分ける

後半系列では、構文・型と現在の入力に対する参照の実在を検証してから、継続可能な保存物を作る。一方、人物・値・版・元IDが正しいか、挙げた資料がその内容を本当に支えるかは意味採点で調べる。採点の正解表を、モデルの入力や保存器の修理には使わない。

**採点の実行主体。** 本稿の成績に用いた意味採点は、有限語彙の合成課題に対する決定論的なPythonコードで実行した。人物・観測値・版・元ID・参照・処理状態を、各試験で固定した期待値と入力支持条件に照合する。答案ごとに別のLLMや人間が自由文を解釈して成否ラベルを付ける工程は置いていない。「意味」は型の適合を越えて内容を照合するという意味で、自由文を別モデルに判定させる方式を指さない。

| 試験 | 固定採点の入口 |
| --- | --- |
| SC01・SU01 | 各analysisモジュールの`analyze`、`shared_score`／`score_fields`等 |
| RD01・SC02・SC03 | RD01の`score`、SC02の`analyse`、SC03の固定codec＋同採点 |
| SU02・SR01 | 各designモジュールの`analyze`と固定の比較・支持条件 |
| SM01・SM02・RC01・RC02 | 各designモジュールの`score`／`evaluate`／`score_normal`等 |
| E1・E2 | `paper01_pair_design_v1.py`の`e1_evaluate`（凍結RC02採点を使用）／`e2_evaluate` |

LLM支援には評価規則・コードの作成と事例説明が含まれる。固定コードにも操作化・実装の誤りはあり得るため、保存回答からの再計算、成分の照合、コードの開示を組み合わせる。再計算一致を独立した第三者による再採点とは扱わない。[凍結採点コードと依存の一覧](references/analysis/paper-01-rereview-20260922/scorer-source-manifest.json)。

| 入力・出力の状態 | 門番／保存側の扱い | 意味評価で調べること |
| --- | --- | --- |
| 必須欄なし、重複キー、型違い | 構造不備として継続を止める | 独立に読める別欄の情報は残す |
| 現在入力に存在しない記録名・選択先 | 参照・選択を拒否する | 不在の参照を正しい出典へ直さない |
| 実在するが古い行・別人の行を選ぶ | 構造上は通り得る。その行を保存する | 新旧、人物、値、出典の適合 |
| 型は正しいが、元IDだけ誤記 | 構造上は通り得る。誤記を保存する | 正式な元IDと入力による支持 |
| 実在する資料を余分に根拠へ列挙 | 実在検査だけでは通り得る | 列挙した各資料が採用行を支えるか |

この分離により、RC01で誤った元IDが門番を通った後も、正しい値と一緒に保存され、PROBEへ渡る過程を観測できた。意味誤りを通すことは本実験の観測方針であり、実運用の安全な保存条件がこれで十分という提案ではない。[RC02の構造・参照検査](references/scripts/row_carry_02_design_v1.py)（原コード行110）、[意味採点](references/scripts/row_carry_02_design_v1.py)（原コード行157）

### C.3 観測行を、人物・値・版・出典のまとまりとして運ぶ

SELECTの共同観測欄では、モデルが値を書き直す代わりに、現在入力中の採用位置を指定する。A欄の指定例は次のとおりである。これは回答全体ではなく、一つの選択欄だけを示す。

```json
{"record_id":"PARTNER_GROUP","observer":"A"}
```

候補表は、実入力のPRIVATEから本人の一行、LOCAL_GROUPとPARTNER_GROUPからA/B各行を取り出して作る。新しい順に並べ替えたり、正解の人物に一致する行だけを残したりしない。存在確認と型検証の後の処理は、概念的には次の二行である。

```python
selected = current_rows[(pointer.record_id, pointer.observer)]
saved.shared_note.coverage[destination] = deepcopy(selected)
```

この処理が保証するのは、**指定された行の人物・値・版・元IDを、実体化の際に勝手に変えないこと**である。正しい行を選んだことや、元の行が正しいことは保証しない。選択先が実在すれば、旧版や誤った元IDも複製され得る。

記録には、指定先、選択行本文のhash、原回答と実体化後のhash、実入力のhashを結び付ける。モデルによる「選択の正しさ」と、保存器による「複製の一致」を別集計する。RC02のUPDATE、個別ノート、受領票は引き続きモデルが記述するため、この方式は出力全体を決定論化したものではない。[候補表の構成](references/scripts/row_carry_02_design_v1.py)（原コード行207）、[選択の検証・実体化](references/scripts/row_carry_02_design_v1.py)（原コード行241）、[実体化の監査記録](references/scripts/row_carry_02_v1.py)（原コード行149）

### C.4 次入力は、各役の実保存物からだけ組み立てる

RC01・RC02およびE1で状態として引き継ぐのは`memory`であり、その回の`read_receipt`や選択指定は別の監査記録へ保存する。生成したノート全体を無選別に次プロンプトへ連結するのではなく、工程ごとに渡す欄を固定する。

| RC02工程 | 渡す記録 | 持ち込まないもの |
| --- | --- | --- |
| UPDATE | 各役自身の前回PRIVATE・BASE_GROUP、本人の新NOTICE | 担当客の原票による再補充、相手の個別ノート |
| MERGE | 自分が更新したPRIVATEとLOCAL_GROUP、相手が更新したPARTNER_GROUP | 相手の担当客、過去の受領票、正解表 |
| PROBE | 自分のMERGEで実際に保存したPRIVATEとGROUP | 過去の選択指定、別条件の回答、研究上の採点結果 |

研究者が同じ内容のノートを作り直すのではなく、親工程の保存物とそのhashを照合して入力を作る。A/Bの共同部分が同じでも、各役自身の保存物への対応を保つ。保存物の不一致が見つかった場合は処理を止める。

受領票には今回の入力記録名と、その本文hashを結び付ける。これは出力された根拠の検証を助けるもので、モデルが実際にどこへ注意したかを測るものではない。また、古い受領票を保存していることと、完全な由来グラフを自動復元できることも別である。[工程別の入力投影](references/scripts/row_carry_02_design_v1.py)（原コード行75）、[memoryの抽出と受領票の結合](references/scripts/row_carry_02_v1.py)（原コード行159）

### C.5 生成に渡す要求と、返ってくる応答の両側を検査する

研究用の生成要求は管理側が組み立てる。実装上の設定は`tools=[]`、`tool_choice="none"`、`parallel_tool_calls=false`で、固定指示と課題資料の二つのメッセージを渡す。予定した要求bytesのhash、許容キー、モデル名等を送信前に確認し、予定外の欄やツール定義を受け入れない。

戻りのストリームも許可したイベントと出力項目を検査し、ツール呼出し等の許可していない出力項目や未完了・切断を研究回答として採用しない。構造検証に渡す回答テキストと、生の受信証拠を区別して保存する。これらはプロンプト中の「余分なことをしないで」という依頼とは別の受け口である。

この説明は当時の実装契約を示す。任意の外部サービスで同じ動作が保証されることや、一般的な攻撃耐性を立証したという意味ではない。RC02ではこの経路で24回答を取得したが、ツール逸脱の発生を実測して防いだ試験ではなく、拒否経路の確認は合成例と既存テストによる。[要求の構成](references/scripts/research_controlled_sender_v3.py)（原コード行50）、[入出力の検査](references/scripts/research_responses_gate_v3.py)（原コード行20）

### C.6 欠測・再送・停止を、結果の良し悪しから切り離す

各要求には予定IDと親依存を定め、工程の終了を確認して次へ進む。RC02では、片役のUPDATEから使える保存物が得られなければ同組のMERGE二件とPROBE二件を未発行にし、MERGE一件の不備ならその役のPROBEだけを未発行にする。最終のPROBE回答を新しいメモリとして再投入しない。

読める範囲の既知誤りと、読めない範囲の不明を別々に残す。組単位の結合は、既知FalseがあればFalse、そうでなく不明があれば不明、すべてTrueならTrueとする。予定分母を小さくして完全取得例だけの成功率に変えない。

再送は、本文のない明示的な混雑応答に限って同じ要求bytesで行う。RC02では失敗から30秒後、同じ論理枠に追加一回、全体追加四回までとし、要求数・時間の余裕がなければ停止する。形式・意味の修理をモデルへ求める再送はこの試験では行わない。以前の別系列に理由欄の限定再提出機構があっても、RC02で使用したものと混同しない。実測では再送・欠測はいずれも0であり、これらの例外経路が実測で発火したとは扱わない。[再送条件](references/scripts/row_carry_02_v1.py)（原コード行38）、[親依存と保存照合](references/scripts/row_carry_02_v1.py)（原コード行317）

### C.7 保証の強さを、確認方法ごとに記録する

指示、schema、素材、割付、コード依存、保存元、要求bytesをhashで結び付け、取得中の変更を検出する。hashは同じ対象が保たれたかの検査であり、意味の正しさを証明するものではない。原回答と派生保存物を分けて残し、生成側とは別の読取りコードで、保存済み証拠から投影・採点・集計の対応を照合する。

| 確認の種類 | 本系列の例 | そこから言える範囲 |
| --- | --- | --- |
| 純粋関数・合成例 | codecの曖昧配列拒否、誤った既存行の無修理複製 | 準備した入力に対する実装動作 |
| 保存を伴う接続テスト | 改変検出、親依存、受領票の分離、再送上限 | 人工的な故障条件での運転動作 |
| 実モデル取得 | RC02の24回答、正しい行選択16/16と複製一致16/16 | この固定材料・実行で観測した成績 |
| 保存証拠の別コード照合 | RC02の2,422項目照合と全24原文の読返し | 保存済み結果と記録の整合。同一プロジェクト内の確認 |

テストの項目数を研究上の独立標本数へ加えない。オフラインでの拒否・変換確認を実モデルの性能改善へ置き換えず、同一作者の別コード照合を独立査読とも呼ばない。[接続テスト](references/tests/test_row_carry_02_connection_v1.py)、[codecの境界例](references/tests/test_shared_note_codec_v1.py)、[別コード照合器](references/scripts/audit_row_carry_02_v1.py)、[取得時の照合結果](references/study2/checks/row-carry-02-live-20260920/frozen-audit.json)

以上の実装は、観測可能な故障を隠さず追えるようにするための足場である。最新行の選択、妥当な更新、適切な根拠、次の判断の正しさは引き続き測定対象として残る。実装上の工夫の一覧を、その各要素の単独因果効果や方式全体の一般的優越性の証拠にはしない。


### C.8 撤回状態と未解決の通知を、次の入力へ保存する

E2では観測行にACTIVE／REVOKEDを持たせ、`processing`へ通知ID、対象出典ID、MATCHED／UNRESOLVED、照合根拠、特定できた観測者を保存する。モデルがこれらを生成し、門番は構造を検査する。管理側が正解人物や失効状態をノートに注入するのではない。意味評価で、全コピーの失効・対象外の保持・処理状態の対応を別に採点する。

後続PROBEは実保存の`memory`と`processing`から作り、原通知や正解IDを再注入しない。これにより、撤回できた記録と未解決の記録を次の判断まで追える。誤IDはDETAILS照合で撤回した場合も履歴として残す。状態の変更と出典文字列の修正を同じ操作にしない。[固定schema・入力投影・意味採点](references/scripts/paper01_pair_design_v1.py)

### C.9 ローカル検査で停止した試行と、承認された継続を別記する

追加二実験の取得器は予定ID・試行番号・親保存物を結び付ける。E2の停止枠では、提供側の完了応答を受けてもローカル検査を通過していないため、通常の研究答案として採用しなかった。後から旧受信記録を再検査して答案へ昇格する処理も行っていない。

継続は旧区間を凍結した上で別区間へ保存した。停止枠だけ同一bytesで第2試行を行い、その他62枠は初回発行、前回129回答はそのまま合算した。区間をまたぐ親保存物1件はpathとhashで指定した。固定の内容・構造規則、2秒の出力検査を保持し、変更承認の対象を「残枠の取得」に限定した。継続前の合成点検や別コード照合の項目数をモデル標本には加えない。[継続記録](references/analysis/paper-01-pair-resume1-20260921/continuation.json)、[別コード照合](references/analysis/paper-01-pair-resume1-20260921/readback.json)

### C.10 形式補正による参考解析を、原採点から分離する

E1-G23の参考解析は、原227 bytesの最後の`}`のみを除いた226 bytesの派生物を保存し、元の固定評価器と別の読返しで内容・出典・参照を照合した。補正後が正解であることを仮定して成功を代入したのではない。原文・原判定・正式な主解析を保持し、派生解析の唯一の変更枠と変更bytesを記録する。

参考p値は元の式に加え、対応の食違い5対4について二項係数の直接和512/512で確認した。これは算術の照合であり、事後補正を事前規則に変えるものではない。[変更範囲と計算](references/analysis/paper-01-e1-brace-sensitivity-20260921/sensitivity-analysis.json)、[派生回答の照合](references/analysis/paper-01-e1-brace-sensitivity-20260921/derived-evaluation.json)
