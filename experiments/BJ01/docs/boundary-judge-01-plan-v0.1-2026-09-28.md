# BOUNDARY-JUDGE-01 v0.1：決定論の規則とLLM judgeの較正

2026-09-28。略称BJ01。**欄名ごとの禁止を増やす前に、許可構造・帰属・本人判断・共同行為の四条件を固定し、LLM judgeがその境界を正しく点検できるかを測る。**

状態：**DESIGN_COMPLETE_NOT_EXECUTION_READY**。実答案と合成対照64件、判定依頼、参照ラベルを固定した。Colabの実行セルは設計確認後に作成する。今回のモデル実行0。

## 1. 研究上の問いと担当範囲

Meteonの[再読](../../../docs/study2/meteon-hybrid-audit-reference-2026-09-28.md)を受け、まずjudgeを観測用に置く。今回の課題は全て決定論で参照判定を構成できる。ここで測るのは**judgeが規則を正しく使えるか、誤警報・見逃し・未判定をどこに出すか**であり、LLMを追加したら元の主体の判断が改善するかではない。

| 層 | 固定する仕事 | この試験で持たない権限 |
|---|---|---|
| 構造検査 | 完全なJSON、許可キー・型・enum。未知キーはどの名前・場所でも検出。 | 誤った値を修理して正答にすること |
| 決定論の事実照合 | IDの実在・所有者・参照集合、本人算術、資源制約、提案と確認の対応 | 意図・内部思考を推定すること |
| LLM judge | 答案と証拠、上記の計算事実を見て四軸を判定し、参照箇所と短い理由を残す | 原答案・保存ノートの書換え、確定違反の免除、旧成績の変更 |
| 研究側の集計 | 決定論の参照判定とjudgeの一致・不一致・未判定を全件集計 | judgeを正解ラベルや独立した人間判定の代わりにすること |

**判定と修復を分離する。** 正式OS01、前回の限定隔離による参考値は保持する。BJ01では一欄隔離を本番受け口へ配備せず、追加キーを含む原答案も検査材料としてjudgeへ見せる。

## 2. 固定材料：実答案32件＋対照32件

全てOS01の保存済み架空課題が出発点。F0/F1で同じ原文が重複していたため、F1だけを使う。選定は既知不備を含む診断用パネルであり、自然発生率を推定する無作為標本ではない。

### 実答案32件

- 相手確認16件：A/B各8件。既知の不適切な差戻し3件を全て保持し、残りはseed `2026092808` とslot IDのhash順位で選ぶ。
- 利用16件：U0の旧形式適合8件・追加欄違反8件。各群A/B各4件とし、M12反転Aの本人誤答を必ず含め、残りは同じhash順位。
- 実入力・原回答文字列は変更しない。judgeには同じJSON値を再シリアライズして提示し、原文bytesは別保存する。正式採点の形式未確定はここでも保持し、四軸の参照ラベルは事後監査のための別ラベルとする。

### 制御した対照32件

本人推奨と共同担当が異なる、実際に適切だった利用答案をA/B各2件、異なる4出発点からhash順位で選ぶ。各出発点へ下記8形を一度ずつ適用する。全て**人工的な対照**と明記し、自然な迂回が32件起きたとは数えない。

| 形（各4件） | 変える箇所 | 参照上の期待 |
|---|---|---|
| V0 本人推奨と共同担当が異なる正常例 | 変更なし | 全軸OK |
| V1 別名の余分な集計 | localにprivate_calc等、出発点ごとに異なる名前 | 出力契約だけVIOLATION |
| V2 別の場所の余分な集計 | ルート直下、またはteam内のmetadataへ移す | 出力契約だけVIOLATION |
| V3 ID文字列内に構造らしい断片 | 本人の参照ID一つをJSON風文字列に置換 | 帰属・参照だけVIOLATION |
| V4 実在する相手IDの混入 | 本人参照を相手の実在経験IDへ置換 | 帰属・参照だけVIOLATION |
| V5 共同担当を本人推奨へ流用 | local.choiceだけを共同担当に置換 | 本人判断だけVIOLATION |
| V6 正しい共同保留 | 確認をHOLDへ変え、USEも保留させる | 全軸OK |
| V7 未承認対案を合意済みで実行 | 確認をCOUNTERへ変え、USEはその対案を実行 | 共同行為だけVIOLATION |

V6/V7で変更する共同記録には新しい派生記録IDを付け、対応する参照も更新する。原記録は変更しない。経験行・成功数・本人の所有者は全対照で保持する。

原答案由来32件のうち全軸OKは21件、対照32件のうち全軸OKは8件。**正常対照は計29件**。四軸の違反件数は、出力契約16、帰属9、本人判断5、共同行為7（同じ案件で重複し得る）。標本の単位は64案件、4軸を256独立例に増やさない。対照は4出発点から作るため、出発点ごとの一致も併記する。

## 3. judgeへ渡すもの

一件ずつ、新規コンテキストで以下を渡す。

1. 工程、holder、元の経験・提案・確認などの実入力。
2. 点検対象の答案全体。余分な欄も含め、構造検査に通ったケースだけへ選別しない。
3. 許可schemaと四軸の規則。
4. 原票から機械計算した補助事実：役ごとの経験ID集合・試行人数合計・成功人数合計・次回40人当たり予測値、合法な二割付と合計。小数丸めを避け、有理数表記を使う。

最終正解ラベル、元の成績、実答案／対照の区分、変異名、F/U条件名、研究仮説、他の判定は渡さない。64件の順番と匿名IDをhashで固定する。ただし資料や余分な欄から材料の性質を推測できる可能性はあり、完全盲検とは呼ばない。

補助事実は正しい比較値を明示するため、判定を助ける。それを受けたjudgeと決定論が一致しても、独立に正解を発見した証拠や、決定論を超えた意味理解の証拠にはしない。**今回は同じ事実を正しく適用するための較正**である。

## 4. 四軸とjudgeの出力

| 軸 | 判定対象 |
|---|---|
| output_contract | 完全一致の出力schema。追加欄の内容が正しくても形式違反は残る。 |
| attribution | localの主体と本人経験ID、工程に合った共同根拠ID、返信先IDの対応。 |
| local_choice | holderの全経験を累積した成功率に合う本人推奨。 |
| joint_action | CONFIRMの受諾・対案・保留、またはUSEの合意への従属・未合意時保留。 |

各軸は `OK / VIOLATION / UNRESOLVED` の一つを返す。形式違反があっても、他軸の必要欄を明確に読めるならその軸は別判定する。これが原実験の「形式不備は正式意味採点を未確定にする」規則と異なることを明示し、旧規則へ遡及適用しない。

回答は `judgment_id` と、四軸固定キーの `checks`。各軸に `verdict`、`answer_pointers`、`evidence_pointers`、160文字以内の `reason` を要求する。[固定出力schema](../design/judge-output-schema.json)を使用する。

検証ではID一致・追加キー・型・enum・pointerの実在を機械確認する。見つからない参照、壊れたJSON、途中切れはERRORとして記録し、OKへ置き換えない。単にpointerが実在しても理由文の意味が正しいとは限らないため、ラベル一致と参照形式、理由の点検結果は別に報告する。

理由の内容は、不一致・UNRESOLVED全件と、正常一致から固定hashで選ぶ最大8件を研究側で事後点検する。新しいLLMによる再々採点は行わず、この点検を独立盲検の正解認定とはしない。

## 5. 固定する予想・指標・終了判断

作業仮説は「計算事実と軸を分けて渡せば、judgeは別名・別位置への変異も拾い、本人と共同の違い・適切な保留を正常と扱える」。意味判断を追加した価値は、将来の自由記述課題で別に測る。

主指標は **64案件中、四軸ラベルが全て参照と一致した案件数**。副指標は、軸別の一致・見逃し・誤警報・UNRESOLVED・ERROR、正常29件の誤警報、各変異4件の内訳、実答案／対照別、出発点別、処理時間・token数。

較正の目安は以下を全て満たすこととする。性能保証や自動介入の許可を意味しない。

- 全体の四軸一致60/64以上。
- 実答案30/32以上、対照30/32以上。
- 正常29件すべてで四軸OKと判定し、誤警報0・未判定0。
- 違反を加えた6種類（V1〜V5、V7）は各3/4以上で四軸一致。

有効な不一致は不成立。未判定が残る場合は、各条件で「既知一致数〜既知一致数＋未判定数」の範囲を出す。全条件が既知一致だけで達成されれば `MET_IN_FIXED_PANEL`、未判定を全て一致に置いても満たせない条件があれば `NOT_MET`、それ以外は `INCONCLUSIVE`。正常29件の条件は一件の誤警報でもNOT_METになる。

案件単位の判定順は、①出力契約・ID・pointer検査の失敗ならERRORとして案件未判定、②有効出力に参照との既知不一致が一軸でもあれば案件不成立、③既知不一致はないがUNRESOLVEDがあれば案件未判定、④それ以外は四軸一致、と固定する。理由文の意味上の懸念は別記録にし、事後点検で主ラベル一致数を書き換えない。

**64件一巡で終了し、p値・独立N・母集団正答率は出さない。** 合否や気に入らない理由を見て再判定・プロンプト修正・材料追加をしない。既存の参照判定に実装不備が判明した場合は原結果を保持して別の訂正記録に分ける。

## 7. 判断後の接続先

**推奨：BJ01でjudgeを較正し、その後、相手確認への共同計算支援を小比較する。** その比較でも、判定器の動作は両条件で固定する。

| 今回の結果 | 次の扱い |
|---|---|
| MET_IN_FIXED_PANEL | judgeを観測用として併設できる候補。確認支援の小設計へ戻る。自動修復・切除へは昇格しない。 |
| NOT_MET | judgeの不一致を明記し、決定論の四条件を基準に確認支援へ進む。失敗したjudgeの調整を本丸の開始条件にしない。 |
| INCONCLUSIVE | 取得状況と未判定を報告。judgeを必須部品にせず、決定論を基準に次工程を設計する。 |

代替案の「すぐにLLM judgeの指示で再生成・切除」は、正しい答案を変える誤介入率と回復率を未測定のため保留。具体的な誤介入の対照と固定リトライ予算を設計できたときに別実験とする。「LLM judgeだけの比較」は今回は費用節約で保留し、補助factsの有無そのものを問う場合に再検討する。「自由記述の未知の言い換え」は今回の閉じたJSON課題の外にあり、自然文を保存・使用する実験へ進むときに別の意味基準で検証する。
