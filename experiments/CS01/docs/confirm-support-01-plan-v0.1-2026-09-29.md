# CONFIRM-SUPPORT-01：相手の確認にも共同候補の合計を添える小比較

2026-09-29／設計案v0.1、略号CS01。**本人の推奨を保ったまま、相手の適切な共同提案を確認し、その後の仕事へつなげられるか**を測る。昨日の方針同意と本日の再開指示を受け、材料・比較・採点・終了条件を具体化した。現時点は設計とオフライン点検まで。

## 1. 今回、何を変えるか

[OS01](../../OS01/docs/own-summary-01-result-2026-09-28.md)では、本人用と共同用の集計を分けると、提案と本人利用は全件適切になった。一方、相手確認では、正しい共同提案を資源制約に反する案へ差し戻す三条件が残った。相手確認には、共同候補の一覧や合計をまだ提示していなかった。

そこで、同じ保存済み提案から確認をやり直す二条件を比べる。

| 条件 | 相手確認に渡すもの | その後の二人の利用 |
|---|---|---|
| BASE：確認支援なし | 元の全経験、以前の記録、今回の本人判断・共同提案 | 今回の実確認と本人用集計を渡す |
| SUPPORT：確認支援あり | BASEと同じ資料＋**実行可能な二案と予測合計** | BASEと同じ規則で渡す |

共同候補表は、例えば「A紙・Bデジタル＝49人」「Aデジタル・B紙＝47人」と示す。どちらを承認・提案するかはLLMが答える。本人の推奨はその人の経験で決め、共同担当と区別する。本人は紙推奨でも、資源を分け合う共同作業ではデジタルを担当することが正答になり得る。

**今回の介入は、合法候補の列挙と計算済み合計を一緒に供給する支援。** 候補の見える化、算術支援、配置、入力長を個別には分離しない。まず確認段階全体を助けるかを見る。

## 2. 主比較は既存の全32条件、192回答

OS01のF1提案から、16出発点×反転／補強の32条件を全部使う。三失敗だけを選ばず、確認が成立していた条件も含む。F0/F1の確認は同一原文だったため、F1だけを採る。元の本人判断・共同提案は全32条件で適切であることを保存物から照合済み。

```text
保存済みの同じ提案 ─┬─ BASE：新しい相手確認 → A利用・B利用
                    └─ SUPPORT：新しい相手確認 → A利用・B利用
```

各条件で確認2回答＋利用4回答、32×6＝192回答。提案の新規生成はしない。過去の確認・利用回答は新結果へ流用しない。二条件とも同時期に新しく生成し、今回のBASEを比較対象にする。

32は16出発点からの対応した経験条件数である。元履歴集合1／2は過去の実行に由来し、今回の同一入力の新しい2反復を意味しない。各セルの新規測定は1回。既知材料を使う適応的な工程比較として報告する。

## 3. 無条件承認を見分ける8対照、16回答

主比較の入力提案はすべて正しいため、ACCEPTを常に出すだけでも承認数は上がる。その読みを区別するため、以下の誤提案を各4条件作る。

| 対照 | 提案の変更 | 適切な確認 |
|---|---|---|
| 合法だが劣る案 | 二つの合法候補のうち、予測合計が小さい方へ割付を交換 | 最適な合法案をCOUNTER、またはHOLD |
| 資源制約違反 | 確認役の本人推奨と同じ媒体をA/B双方へ割当て | 最適な合法案をCOUNTER、またはHOLD |

8条件×二支援条件＝16確認。対照では後続USEを生成しない。COUNTER／HOLDの内訳と、ACCEPT、誤った対案、参照不備、本人判断の不備を別掲する。HOLDは元の指示契約で許容されているため適切確認に含むが、最適対案を作れた件数とは分ける。

選定は強弱×本人推奨同異×反転／補強の8区分から各1件。異なる8出発点を使い、各対照型でも確認役A/B各2、元履歴集合1/2各2になる集合を、seed `2026092901` を含むhash順位で一意に選ぶ。成績・三失敗の包含を選定条件にしない。

変更は提案の割付と、派生提案であることを示す新record_idだけ。経験、人物、本人判断、経験参照、候補表、提示順は保持する。対照名・変異名・期待回答はモデルへ見せない。これは研究者が作った誤提案への診断であり、自然発生率や独立8材料の一般化には使わない。

## 4. 供給する値と、引き継ぐ記録

SUPPORTの確認入力に `joint_candidate_totals` を一つ追加する。各行は元提案時の候補ID・A/B割付・`projected_total_success_per_40_each`。元の候補順を保持し、合計で並べ替えず、最適ラベルやACCEPTの正解は付けない。

予測合計は、各役について `40×その媒体の累積成功人数÷累積試行人数` を計算し、その候補の担当媒体に従って二役分を足す。実際の全経験5行から再計算し、凍結資料と一致することを接続時にも確認する。集計は派生値であり、新しい経験や出典IDにはしない。

確認役の本人用集計は、今回CONFIRMには加えない。本人判断と本人参照への影響も結果として測る。確認プロンプトはBASE/SUPPORT共通で、候補表の意味と入力専用であることを説明する。出力schemaは従来の `local` と `reply` のまま。replyの割付はLLMが記述し、候補ID選択への変更・割付の機械的修正は行わない。

主比較の後続USEでは、以下を両条件共通で行う。

- 更新本人は、OS01で実際に保存した本人判断を使う。
- 相手は、今回のCONFIRMが実際に出したlocalを本人判断として使う。
- 共同記録は、元の実提案と今回の実replyを二役の元表示順で並べる。action、割付、reply_to、経験参照を修理しない。
- 本人用の集計は、各holderの経験だけからあらためて計算して添える。共同候補表や共同合計、条件名、採点結果は渡さない。

新しい本人判断・確認記録のIDは、実験名・packet・役・欄からhashで作り、条件名を含めない。同じpacketのBASE/SUPPORTは同じID命名を使い、別々の文脈で保持する。これによりUSEの比較へ別のID表記差を加えない。

## 5. 出力契約と意味を別に検査する

構造検査は決定論で行う。本人localはsubject／choice／evidence_refsの三キー、CONFIRMはlocal／reply、USEはlocal／teamのみ。A/B固定キー、許容enum、ID、型、重複・過不足、資源制約、合意条件を検査する。

受け口は既存の生JSON／既知の完全外装だけの正規化を継承する。**未知キー削除、OS01で使った一欄隔離、値修理、再生成を採用しない。** 入力の集計と指定回答欄を分ける説明文を両条件へ共通に加え、検査もその契約と一致させる。OS01正式／参考成績は保持する。

[BJ01](../../BJ01/docs/boundary-judge-01-result-2026-09-28.md)のjudgeは今回の実行系へ組み込まない。今回の四軸は固定規則で判定できるため、追加のLLM判定0。自由記述の理由も要求しない。結果が出た後は、不成立・未確定の全応答とそれらの親資料、正常な主経路から固定hash順位で最大8経路を主担当が非盲検で資料照合し、疑義を別記録に残す。正常例はJ成立の経路を対象に、UTF-8文字列 `CS01-review|2026092901|経路ID` のSHA256を昇順に並べて選ぶ。主ラベルを裁量で置き換えない。

## 6. 主指標は、確認役の判断と確認行為の両立

主比較は、主32条件における **V＝本人判断Lが適切、本人参照Z_localが適切、相手への応答が適切** の成立数で、SUPPORT−BASEを取る。

主入力はすべて最適で合法なので、適切応答は「ACCEPT、提案と同じ割付、正しいreply_to、五経験の正しい参照」。単なるACCEPT件数はVと別掲する。誤提案対照では、正しい参照を付けた最適COUNTERまたはHOLDを適切応答とする。

| 評価 | 各条件の予定分母 | 内容 |
|---|---:|---|
| V（主比較） | 32確認 | 本人と参照を守った適切確認 |
| L／Z_local／適切応答／K／C | 各32確認 | 本人判断、本人参照、応答契約、合意、最適な合意の内訳 |
| 本人利用・相手利用 | 各32回答 | 各役のLとZ_local。保存判断の正誤別にも表示 |
| Hと利用参照 | 各64回答 | 合意への忠実な実行、未合意時の適切保留 |
| J | 32経路 | 確認V、最適合意C、二役USEのL/H/Zがすべて成立 |
| Q | 16出発点 | 同じ出発点の反転・補強でJが両方成立 |
| S_target／I_peer | 各16出発点 | 両経験条件で、更新本人／相手の判断を形成から利用まで保つ |
| 対照の本人込み適切応答D | 8確認 | 誤提案をそのまま承認せず、本人L/Z_localと応答契約を満たす |

S_targetは保存済み提案の本人Lと更新本人USEのL、I_peerは新しいCONFIRMの本人Lと相手USEのLを両経験条件で要求する。元提案は全件適切だが、その確認済み前提も証拠に残す。新確認で誤った本人判断を保存し、USEで経験から正しく回復した場合、局所回復と経路Jの不成立を両方記録する。

## 7. 予想・固定目安・欠測

方向予想は **V_SUPPORT > V_BASE**。共同候補の供給で確認を助け、本人の参照と後続利用を損なわないと予想する。両条件とも天井なら支援の優位を確認しなかったと結ぶ。

SUPPORTを対象に、二段の工学的目安を固定する。BASEも同じ内訳を表示する。

1. 確認目安：V≥30/32、確認L=32/32、Z_local=32/32、対照D=8/8。
2. 後続両立目安：Q≥14/16、元履歴集合別Q≥7/8、強弱別Q≥7/8、S_target=I_peer=16/16。前系列の目安を維持する。

既知成立だけで全条件を満たせばMET_IN_FIXED_SAMPLE、未確定を全成立にしても一項目でも届かなければNOT_MET、その間はINCONCLUSIVE。固定標本での到達点であり、二条件の優位性や一般化の証明とは別である。確認目安を満たしても、後続が未達なら段階を分けて報告する。

形式受理後は意味不備でも保存して続行する。CONFIRMを構造として受理できない場合、その条件の二人のUSEだけを依存欠測とする。対照には子がない。USEの形式不備はその回答だけ未確定。合成指標に必要成分の未確定があれば未確定とし、既知不備も成分別に残す。

主差の下限は `(SUPPORT成立−BASE成立−BASE未確定)/32`、上限は `(SUPPORT成立＋SUPPORT未確定−BASE成立)/32`。欠測上下限であり信頼区間ではない。対になった双方成立／BASEのみ／SUPPORTのみ／双方不成立／未確定を表示する。

固定層別は強弱、本人推奨同異、反転／補強、元履歴集合、本人推奨と共同担当の同異、旧合意の変更／維持／未合意。既知三不備は症例追跡として別掲し、主分母をそれらだけにしない。p値・母集団CI・同一材料を独立Nとした合算は行わない。

## 8. 順序・上限・実行環境

元の経験行・役・媒体・候補順を保持する。主比較の強弱×本人推奨同異×経験条件の各4資料で、BASE先行とSUPPORT先行を2対2にする。対照は全体で4対4。各条件は確認→二役USEの順で完了し、役順は元どおり。主比較を先に、対照を後に固定順で実行する。時間切れで対照に到達できなければ、その欠測を確認目安へ反映する。

seedは `2026092901`・packet ID・工程・役から固定し、支援条件を含めない。同じpacketの二条件に同じseedを使うが、出力の同一性や試行間ノイズの除去を保証しない。対照は別packet IDを持つ。

## 9. この一巡で何を書くか

| 結果 | 結論 |
|---|---|
| Vが増え、対照と後続も成立 | この固定資料では、確認への共同計算支援が本人／共同の両立を助けた |
| 正しい提案のACCEPTだけ増え、誤提案も通す | 承認数の改善と、検証としての適切さを分けて報告する |
| Vは改善するが本人参照やUSEが崩れる | 支援が届いた工程と残った不備を保存物から特定する |
| BASEもSUPPORTも高く差ゼロ | 今回の支援優位は確認しなかった。昨日との差を支援効果にしない |
| 支援後も不適切COUNTER・誤帰属が残る | この候補・合計供給だけでは十分でなかったと閉じる |
| 形式不備や時間切れが残る | 成立／不成立／未確定と欠測上下限を報告して閉じる |

候補一覧だけの第三条件、CONFIRM本人集計の追加、同一セル反復、未使用材料への確認は別の問いとして保留する。今回の結果が介入の内訳を必要としたとき、または構成を確認段階へ進めるときに選ぶ。judge修復や長期化を、この一巡の完了条件へ追加しない。
