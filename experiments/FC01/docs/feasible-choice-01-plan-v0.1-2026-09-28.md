# FEASIBLE-CHOICE-01：本人の推奨と、実行可能な共同配分を分けて選べるか

2026-09-28／設計案v0.1、略号FC01。[EU01の結果](../../EU01/docs/experience-update-01-result-2026-09-28.md)を受けた小比較。**二人の本人判断を保ちながら、実行可能な二案のうち、現在の経験に合う共同案を選び、相手と合意して使えるか**を測る。

今回は設計・材料表・オフライン点検・取得前カードまで。モデル生成0。全文指示・schema・実行採点器・Colab一セルコードは次工程で固定する。

## 1. 何を確かめるか

EU01では、本人の選択的更新と相手の判断保持は各16/16組で成立した。一方、全32共同提案は二人の本人推奨を並べた割付と一致し、本人推奨が同じ16件では紙／紙またはデジタル／デジタルとなった。共同作業には紙一つ・デジタル一つしかないため、その16件は成立しなかった。

例えば、二人とも自区画には紙を薦めるのが正しくても、共同作業では片方がデジタルを担当する必要がある。**本人の推奨を変えることと、その日の共同担当を変えることを分けられるか**が今回の焦点である。

出力上の一致は分かったが、モデル内部で本人欄をコピーしたことまでは分からない。今回は、提案の書き方を変えた比較で、選択・本人判断・合意・後続利用のどこが変わるかを追う。

## 2. 二方式は、同じ二候補を見て答える

実行可能な割付は次の二つだけである。

- Aが紙、Bがデジタル。
- Aがデジタル、Bが紙。

この二案を、**両方式に同じ候補表として提示する**。候補には中立なID `X` / `Y` を付ける。合計点、優劣、正解の印は付けない。

| 方式 | 本人欄 | 共同提案の回答 | 実行器の処理 |
|---|---|---|---|
| **直接記述 DIRECT** | 自分の経験から推奨と根拠を書く | A/Bの割付と根拠を書く | 書かれた割付をそのまま保存 |
| **候補選択 SELECT** | DIRECTと同じ | 候補IDと根拠を書く | 選ばれた候補のA/B割付を、その候補表から複製 |

両方式で、本人欄は `subject / choice / evidence_refs`。DIRECTの共同欄は `allocation / evidence_refs`、SELECTは `candidate_id / evidence_refs` とする。SELECTの複製器は候補IDを受け取るだけで、経験の集計・最適案の計算・選び直しを行わない。

この比較が調べるのは、**候補表が共通にあるときの、直接記述と選択＋複製という出力契約の差**である。候補表を見せる効果は両方式に含まれる。DIRECTもEU01にはなかった候補表を見るため、EU01の旧回答を対照成績に流用せず、両方式を今回新しく生成する。

候補選択では、正しくIDを選んで複製できれば、資源違反の割付は生成されない。これは実装の性質である。**実測の中心は、その二候補のどちらが適切かを選べるか**であり、資源適合だけで成功としない。

## 3. 出発資料と、数える単位

EU01の全16出発点×反転／補強の全32条件を使う。前回の成功・不成立による抽出はしない。EU01で使用した初回PROPOSE入力から、以下をそのまま継承する。

- 旧経験4行と本人に届いた新経験1行。数値・ID・行順・媒体表示順を保持する。
- AC01の実際の本人判断二つと旧共同記録。旧合意15出発点と、未合意のM05も含む。
- 新経験の受取役が提案、相手が確認、最後にA/Bがそれぞれ利用する役割。

EU01の終了時の誤った提案・確認を直す実験ではなく、**同じ出発入力からの新しい方式比較**である。新経験の追加回数も増やさない。

32条件のうち、現在の本人推奨が同じもの16、異なるもの16。今回はこの区分を実行前に固定して両方を報告する。区分は経験の算術から作り、前回の成否を材料の選択規則にしない。

元資料は8配置×2保存履歴からの継続であり、反転／補強、方式、工程も依存する。各新規生成セルは一回。32条件や256回答を独立した新規標本数とは扱わず、p値・母集団CIは出さない。

## 4. 正しい判断と表示順

EU01の算術を継承する。本人の経験は各媒体80人、相手は40人である。本人推奨は自区画の累積成功率が高い媒体。共同案は各区画40人への予測成功人数を合計する。

`役・媒体の予測成功人数 = 40 × 全回の成功人数の合計 ÷ 全回の試行人数の合計`

全32条件で共同最適案は一意。反転条件の二候補の差は3人または11人、補強条件は7人または15人。本人推奨と共同担当が違っても、その役の本人判断を不正解とはしない。

例えばM01の補強条件では、Aの予測は紙28人／デジタル17人、Bは紙27人／デジタル23人となる。本人推奨は二人とも紙でよい。共同案はA紙/Bデジタルなら51人、反対なら44人なので、共同ではBがデジタルを担当するのが適切である。このときもB本人の推奨は紙のままでよい。

候補IDと表示位置を固定的な正解の手掛かりにしないため、候補名の割当と表示順を別々に反転する。`b=配置ブロック−1`、`r=元反復−1`、`e=反転0／補強1` とし、X/Yへの割付対応は `(b+r+e) mod 2`、X/Yの表示順は `(r+e) mod 2` で反転する。初期対応はX＝A紙/Bデジタル、Y＝Aデジタル/B紙、初期順はX→Y。

これにより、正解ID×正解表示位置の四通りは全32条件で各8件、本人推奨の一致／不一致層・反転／補強層で各4件になる。同じ条件のDIRECTとSELECTは同じ候補表・表示順を使う。採点用の正解IDや合計点はモデルへ送らない。

## 5. 提案だけに介入し、その後を共通にする

```text
同じ出発資料＋同じ二候補
  ├ DIRECT：本人判断＋共同割付を書く
  └ SELECT：本人判断＋候補IDを書く → 割付を機械複製
       ↓ それぞれ独立した系列
  相手の確認：本人判断＋ACCEPT / COUNTER / HOLD
       ↓
  A/Bの後続利用：本人判断＋共同担当／共同だけ保留
```

PROPOSE後の共同記録は、どちらも `allocation / evidence_refs` という同じ形にして相手へ渡す。SELECTの候補ID→割付の変換だけが新しい決定論的処理であり、本人欄と参照IDは実回答のまま引き継ぐ。DIRECTの不適切な割付も、構造が有効ならそのまま渡す。

原回答、候補表とそのhash、選択ID、変換前後、著者・記録ID・親hash、次入力を保存する。共同記録IDは条件間で中立な同形の規則を用い、後続入力には方式名・選択ID・成績・機械検査の合否を加えない。相手は今回の記録を見て判断する。

CONFIRMとUSEの全文指示・schema・採点は、EU01の対応工程を継承する。候補表はこの二工程へ追加しない。確認で不適切な対案が出ても修理せず、結果として数える。全経験5行の再掲も継承する。

合意Kは、正しい相手提案IDへのACCEPT、二役の割付一致、紙一つ・デジタル一つ。適切な合意CはKに現在の最適性を加える。COUNTERは相手の承認を得ていないため合意にしない。

USEはKがあればその割付へ忠実に従い、なければA/BともUNDECIDED、basis=UNRESOLVEDとする。Kがある場合はbasis=SHARED_DECISION。どちらも新提案と確認の二記録を根拠にする。旧合意へのフォールバック、未成立時の具体割付をコードで消す実行許可処理は今回加えない。前回の保留不備が残るかも、そのまま測る。

## 6. 形式不備・選択不能の扱い

SELECTの候補IDとして、X/Yと明示的な保留UNDECIDEDを指示する。UNDECIDEDはA/BともUNDECIDEDへ変換し、共同案としては不成立のまま相手へ渡す。DIRECTも両者UNDECIDEDを答えられる。今回の資料には常に一意の最適案があるため、保留は最適提案の成功に数えない。

文字列型だが未定義のID、大小文字違い、別候補の綴りなどは原文を保存し、**候補結付け不備**として数える。文字を直す・近い候補を選ぶ・正解へ置換する処理はしない。この場合は割付を作れないため、その分岐の確認と二USEを依存欠測とする。提案の適切さは既知の不成立、後続の実測は未確定として分ける。

必要キーや型、JSON構造、EOSに不備がある場合は取得・構造欠測。既知の完全なJSON外装だけを決定論的に処理する。意味不備・誤参照・不適切な配分・COUNTER/HOLDは、受渡し可能なら後続へ進める。結果を良くするための再生成はしない。

## 7. 指標と比較の読み方

| 指標 | 測るもの | 各方式の予定分母 |
|---|---|---:|
| F / O | 提案の資源適合／現在の最適案への一致。二つを別列で示す | 各32提案 |
| **P：本人判断を保った適切提案** | PROPOSEの本人Lと本人参照Z、共同案Oと五経験参照Zがすべて適切 | **主比較32条件** |
| L / Z | 工程別・役別の本人判断／本人と共同の参照・basis | PROPOSE32、CONFIRM32、USE64 |
| K / C | 合意関係／その合意の現在最適性 | 各32経路 |
| H | USEが実合意へ従う、または合意なしを正しく保留する | 64回答 |
| J | 各条件で全工程の本人L・参照Z、C、二USEのHがすべて適切 | 32経路 |
| Q | 同じ出発点で反転・補強のJが両方成立 | 16組、元反復ごと8 |
| S_target / I_peer | 両条件の形成時とUSEで、本人／相手の本人判断Lがすべて適切 | 各16組 |

**主比較はPのSELECT−DIRECTの差と、対応する条件の内訳**（両方式成立・DIRECTのみ・SELECTのみ・両方式不成立・未確定）とする。Oと各L/Zを並べ、Pの差が候補選択・本人判断・参照のどこから来たかを分ける。下流はC/J/Qとして追う。参照や読出しの不備で、適切提案そのものの改善を隠さない。

本人推奨が同じ16／異なる16、反転16／補強16、元反復ごと16条件、旧合意の変更／維持／新形成を固定の補助内訳とする。主たる予想は、SELECTでPがDIRECTを上回り、本人判断の保持を損なわないこと。差ゼロや逆方向も、そのままこの予想との対応を報告する。

確認済み成立／既知不成立／未確定を予定分母付きで報告する。必要成分が欠測の合成指標は未確定とし、既知の成分不備は別表に残す。差の下限は `(SELECT成立−DIRECT成立−DIRECT未確定)/32`、上限は `(SELECT成立＋SELECT未確定−DIRECT成立)/32`。これは欠測の上下限であり、信頼区間ではない。

次段階への工学的目安は、SELECTの **Q≥14/16、各元反復Q≥7/8、S_target=16/16、I_peer=16/16**。本人の更新と相手の保持を保護条件に置く。DIRECTにも同じ目安を適用し、両方式が到達した場合は共通の候補提示だけでも十分だった可能性を候補として残す。今回だけで候補提示の効果を確定はしない。

すべての下限が目安達成ならMET_IN_FIXED_SAMPLE、どれかの上限が未達ならNOT_MET、その間はINCONCLUSIVE。方式差の主比較と、この進行目安は別の結論として報告する。

## 8. 各結果で何が分かるか

| 結果 | 読み方と、その後の焦点 |
|---|---|
| SELECTでPが増え、本人判断とQも目安達成 | この既知資料では、選択＋複製から共同利用までがつながった。未使用資料か次の更新巡を候補にする |
| 資源適合は保たれるがOが低い | 許された案を返すことと、適切な案を選ぶことを分離できた。選択の計算・資料参照を点検 |
| Pは高いがCまたはHが低い | 提案後の受諾・保留・読出しが残る課題。本人判断の不備と混同しない |
| 両方式とも高い／差がない | 同じ候補表がある場面で追加の選択＋複製の優位は観測されなかった。旧EU01との単純な因果比較はしない |
| SELECTで本人判断が崩れる／成績が下がる | 出力契約変更の負担も含む結果として残す。保護条件未達を隠さない |
| 欠測で差や目安を決められない | 到達工程と未確定を残し、固定一巡を閉じる |

本人の自発的人格、再掲なしの記憶保持、長期共存は今回の射程外。全経験を渡した条件での選択・合意・利用を調べる。第2報は校了のまま、HS02は保留を続ける。

候補提示そのものの効果を分ける第三方式（候補表なしの直接記述）は、同規模なら追加128回答を要するため今回は置かない。両方式が改善して候補提示の寄与を調べたくなった時点で、別設計として検討する。確認・USEまで候補選択へ変える案も、提案後の不備が実測で残るかを見てから扱う。

## 10. 材料と次工程

[材料表](../design/materials-proposal.json)は32共通出発入力・64方式経路・256予定ID、二候補・表示順、採点専用期待値と元ファイルhashを含む。モデル入力は許可した資料欄だけから作り、材料表全体は送らない。材料点検 (see the evidence index)で原ZIP、実入力との一致、独立した分数計算、候補と順序の均衡、予定数と依存関係を確認する。

オフライン点検は2,318項目が通過し、うち1,420は元ZIPのファイルhash照合。検査数はモデルの回答数や独立標本数ではない。初稿では元設計の識別子に版番号が付くことを点検器が想定しておらず停止したため、実ファイルの完全一致値へ訂正した。初稿・停止記録・訂正理由を監査フォルダに保持する。

次は、この設計を確認した後、全文指示とschema、候補結付け・複製、EU01からの共通工程継承、採点と欠測、ZIP再集計を実装する。未知ID・不正な直接割付・本人判断だけ不備・非最適な合法案・不適切受諾・未合意の具体割付・構造欠測の合成例を、モデル生成なしで点検する。取得前カード (see the evidence index)。
