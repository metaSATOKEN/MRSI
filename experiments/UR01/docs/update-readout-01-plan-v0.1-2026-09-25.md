# UPDATE-READOUT-01：本人情報を保ち、共同ノートを更新して次へ渡す

2026-09-25／設計v0.1。設計・材料固定・オフライン点検まで完了。実モデル取得・ロード・生成は行っていない。

**次は「読めるノートを、正しく更新できるか」を測る。** [SVR01](../../SVR01/docs/saved-readout-01-result-2026-09-25.md)で成立した四値抽出＋機械計算を後続の読出しに固定し、その前に更新・保存を一段加える。

今回の問いは、**本人の担当客情報を保ちながら、二人の観測をそれぞれの最新版へ揃え、人物・値・版・出典を一緒に次の判断へ渡せるか**。最新通知で古い行を直す場合と、古い通知が遅れて届いても巻き戻らない場合を、一組の診断にする。

## 1. 比較する二つの保存方式

| 条件 | LLMが書くもの | 保存器がすること |
| --- | --- | --- |
| REWRITE：本文を書き直す | 個別ノート＋共同ノートのA/B行 | 構造が成立した本文を保存 |
| SELECT：行を選び、複製する | 個別ノート＋共同A/B行の候補位置ID | 選ばれた行を、人物・値・版・出典ごと複製して保存 |

**個別ノートは両方式ともLLMが書く。** 機械化する範囲を共同行に揃え、その外側にある本人情報の保持も別に測る。

選択方式でも、古い行や違う人物の行を選んだら、その行が保存される。保存器は最新行を代わりに選ばず、原回答を訂正しない。これによって、選択の不備と転記の不備を区別する。

両条件で更新に使う資料は同じ。指示の共通部分も揃え、求める出力形式を各方式に合わせる。出力schema・出力量・機械処理を含む構成の比較として記録する。

## 2. 材料：修復10件＋巻戻り防止8件

SVR01に使った保存入力から、元の新旧状態に基づいて選ぶ。SVR01での回答・成績を選定コードは読まない。

| 集合 | 保存ノート | 新着通知 | 正しい動作 | 材料数 |
| --- | --- | --- | --- | ---: |
| REPAIR：修復 | 一人の古い観測行が残る | その人の最新通知 | その行を更新し、他の情報を保つ | 10 |
| GUARD：巻戻り防止 | 二人の行が最新 | 一人の古い通知が遅れて到着 | 共同ノートを古くしない | 8 |

REPAIRは既知の古い全10保存物を採用する。最新案内は紙・デジタル各5材料。保持役はA1・B9、通知は本人1・相手9、元保存方式はREWRITE2・SELECT8という元の偏りを保持する。

GUARDは最新一致16保存物から、元保存方式REWRITE/SELECT×保持役A/B×最新案内PAPER/DIGITALの8層各一件をprotocolと元応答IDのhash順で選ぶ。本人の古い通知4件・相手の古い通知4件を割り当てる。紙・デジタル、保持役、元保存方式は各4対4。両集合を合わせて異なる18材料となる。

**通知は原材料に実在する行を再配送する。** 修復側は元の最新通知、巻戻り防止側は更新前の低revision通知を使う。新しい架空の値やIDを研究者が書き足さない。元の個別・共同ノートをそのまま使い、今回の通知と候補一覧を追加する。

ここで「新着」は到着時点を意味し、内容の新しさを保証しない。GUARDを入れることで、「何もしない」と「届いた通知を必ず採用する」を区別できる。オフラインの単純処理でも、何もしなければ修復0/10・維持8/8、通知を必ず採用すれば修復10/10・維持0/8となる。これは材料を点検する合成対照で、LLMの実測成績ではない。

## 3. 入力・候補位置ID・保存の契約

更新入力は元の `holder / scene / item / records` に、一件の `incoming_notice` と四行の `row_catalog` を加える。

| 候補行の由来 | 内容 |
| --- | --- |
| PRIVATE.coverage | 本人の保存済み観測 |
| GROUP.coverage.A | 共同ノートのA行 |
| GROUP.coverage.B | 共同ノートのB行 |
| NOTICE | 今回届いた観測行 |

四行を一覧化する処理は両方式へ同じように適用する。元の内容を変えず、各行には `C1`〜`C4` の候補位置IDを付ける。通知の位置はREPAIRで3・3・2・2件、GUARDで各2件へ分散し、他の三行の順はhash順に固定する。反復では同じ入力を使う。

**C1〜C4は今回の候補の場所、origin_idは観測の出典。** この違いを指示に明記する。SELECTのA/B選択欄はC1〜C4の文字列enumとし、担当役ごとに別の自由記述形式を要求しない。元IDを選択欄へ書いた場合は、別の値へ自動変換しない。

新旧の判定は、同じobserver内のrevisionで行う。Aの番号とBの番号を比較しない。同じobserver・同じrevisionの候補は全欄同一であることを取得前に検査した。PRIVATEとGROUP、通知に同じ最新行が重複している場合、どの位置IDを選んでも同じ内容なら適合となる。

個別ノートでは、担当客の `subject / animal / origin_id` を保ち、本人観測の `observer / paper / digital / origin_id / revision` を最新に保つ。今回の18入力はPRIVATEがすでに最新なので、この工程は個別情報の保持と、共同欄への統合を測る。

共同A/B行は同じ五項目で評価する。値だけ新しく出典が違う場合や、正しい行を違う人物の欄へ置いた場合も記録する。SELECTの保存器は、実際の選択位置・元行hash・コピー先を記録し、選んだ行を全欄複製する。

今回の更新出力には受領票・理由・案内判断を求めない。候補位置の解決と保存の監査を行う契約に絞る。XM01の受領票付き工程とは異なる入力・出力設計であり、以前の厳密成立率を今回の成績へ置き換えない。

## 4. 後続は実際の保存物を読む

各系列は次の二工程となる。

1. **UPDATE**：保存ノート＋新着通知から更新し、構造検査・保存を行う。
2. **READ**：その系列が実際に保存した個別・共同ノートを、新規コンテキストへ渡す。SVR01と同じ指示・schemaでGROUPの四値を抽出し、実抽出値から案内を機械計算する。

READへ新着通知、候補一覧、元の正解、UPDATEの採点は渡さない。個別・共同ノートの本文を実保存物で置換し、元のholder・場面などを保つ。更新に成功した理想ノートで差し替えない。

更新の形式検査は、JSON・必須欄・型・enumと候補位置の解決を扱う。**意味的に誤っていても構造が成立した保存物は、そのままREADへ渡す。** たとえば旧行を選んだSELECTや、形式上有効な誤出典を記したREWRITEも、後続まで追跡する。

UPDATEが構造不成立なら保存物を作らず、そのREADを依存欠測とする。原文と理由を残して、次の独立UPDATEへ進む。JSONの修復、フェンス除去、重複キーの後勝ち、値・列名の変換、意味修正の再生成は行わない。

## 5. 評価と、予定する比較

| 評価層 | 指標 |
| --- | --- |
| 接続 | UPDATEの構造成立、保存可能数、READの実行・形式成立、依存欠測 |
| 個別情報 | 担当客三項目の完全一致、本人観測五項目の完全一致 |
| 共同状態 | 各行の完全一致、四値一致、人物・版・元IDの一致、入力内の実在行との対応 |
| 更新全体 | 個別情報と共同A/B行がすべて期待保存物に一致するか |
| 読出し | 実保存GROUPの四値への転記一致、実保存GROUP基準の案内、最新情報基準の案内 |
| 後続まで | 更新全体が一致し、四値を忠実に抽出し、最新案内まで一致したか |

更新全体と後続までの成績を、それぞれ主たる記述対象にする。後続までの完全一致は両工程の形式成立時に判定し、形式不備・非EOS・依存欠測は未確定として別計上する。READの余分なキーなどで形式が不成立でも、読めた四値等の成分評価は別に残す。更新が正しく保存されていたという事実も、後続欠測で消さない。

全予定系列を分母に、一致・不一致・未確定と欠測上下限を示す。各方式は修復20系列・巻戻り防止16系列。受理された保存物だけを分母にした読出し成績も補助表示し、予定分母と併記する。集合、反復、保持役、通知の本人／相手、通知位置、元保存方式、各材料別の内訳を保存する。

**工程を次へ進める目安は、更新全体と後続までで別々に判定する。**

- 修復18/20以上、各反復9/10以上。
- 巻戻り防止14/16以上、各反復7/8以上。
- 担当客の完全保持36/36。

全条件を観測一致だけで満たせばMET、未確定を全一致にしても届かなければNOT_MET、その他はINCONCLUSIVE。この小比較で次工程を選ぶ目安であり、母集団での信頼性保証ではない。

方式差は修復集合のSELECT−REWRITEについて、欠測下限が＋4/20以上、両反復の下限が正、巻戻り防止集合の差の下限が非負なら、記述的改善信号とする。逆方向も対称に判定する。更新全体と後続までのどちらに信号が出たかを分け、良い方だけを選んで方式全体の勝者としない。p値・母集団信頼区間は算出しない。

## 6. 割付・規模・実行範囲

**18材料×2方式×2反復×2工程＝最大144生成。** UPDATE72回答に加え、保存が成立した系列だけREADを最大72回答生成する。意味上の成否を理由にREADを間引かない。

修復と巻戻り防止を交互に配置する。各材料で両方式のUPDATE、その後に対応するREADを実施し、各呼出しは独立コンテキストとする。方式順は集合別に均衡し、反復2で反転する。新しいprotocolからseedを固定し、同じ材料・反復・工程では方式間のseedを共通にする。反復と工程のseedは分ける。

## 7. 予想と、結果を受けた分岐

予想は、SELECTで共同行を転記する際の損傷を抑えられること。ただし選ぶ行を誤れば旧版が正確に複製され、個別欄の記述は両方式ともモデルに残る。方式全体の差は取得前には確定しない。

| 結果 | 次に検討すること |
| --- | --- |
| 更新・後続ともMET | この契約を使い、二人が別々に更新した記録を交換する一巡へ |
| 更新MET、後続未達 | 保存物を固定し、今回の後続入力で読出しが崩れた場所を確認 |
| SELECTで旧行・別人物を選ぶ | 行選択の契約を一か所見直すか、最新版選択自体をコードへ移す設計を相談 |
| 共同行は良好、個別欄が崩れる | 本人情報の保存境界を別の小比較へ |
| 形式・候補位置の不備が主因 | 接続仕様と内容の成否を分け、未成立経路を先に整理 |
| 両方式とも良好、差が小さい | 両者の成立範囲を報告して閉じ、優越性が出るまで増やさない |

最大revisionの選択もコードで実装できる規則である。今回はその選択をLLMに残した構成を測り、全機械選択による理想保存はオフライン検証の対照に置く。

この一巡では、すでに存在する通知の再配送を通して、個別欄の担当事実と共同欄の二者観測を扱う。新たな経験やスタンスの形成、二人の自発的対話、長期共存は別段階の問いとして保つ。既知の不備に基づく探索的診断であり、独立材料数は18。今回の成績で元のXM01や第一報を書き換えない。

| 保留する枝 | 再検討する条件 |
| --- | --- |
| **更新二方式＋固定読出し（推奨）** | 今回の最大144回答で、選択・転記・読出しの所在を区別 |
| 通知が常に最新の修復だけ | 80回答へ縮められるが、新着追従と版管理を区別できない。今回は遅配対照を残す |
| 全機械による最新版選択 | 誤選択が残り、LLMに選択を任せる必要性を見直す段階で検討 |
| 元IDも含む読出し抽出 | 現時点では保存されたIDを直接採点する。後続でIDを使う撤回・訂正へ進む段階で設計 |
| 二人の生成・交換から全工程を再走 | 更新・保存・後続の一巡が成立してから設計 |
