## 3. 37件は「外側の囲い」による形式不備

37件すべてが、JSONの前後にMarkdownのコードブロックを付けていた。

~~~text
```json
{ … }
```
~~~

内訳はREWRITE25/36、SELECT12/36。事後の原因点検では、全37件が一組の囲いだけを持ち、その内側はJSONとして可読で、各方式のschemaにも適合した。出力の打切りや括弧の破損ではなかった。

今回の取得前規則は囲いを除去しない契約なので、正式には更新の内容評価を未確定とし、保存物を作らずREADをスキップした。この報告でも、内側の内容を新しい成功数へ加えたり、未実施のREADを推定で補ったりしていない。囲いの種類・内側の構造適合という原因診断を別記録に残した。

たとえば `UR01-R08-R1-REWRITE` はこの形式だった。原文とhashは[説明用の原文集](../../../supplements/update-readout-01-result-20260925/examples.json)に保存した。

## 5. 古い行を保った10件と、巻き戻った1件

修復側では、REWRITE5件・SELECT5件が、修復すべき古いGROUP行をそのまま残した。この10件は全件、後続の案内も最新情報とは異なった。巻戻り防止側ではSELECT1件が遅配された旧通知を採用したが、こちらは案内の答えが変わらなかった。

説明用に選んだ次の二例は、成績集計後の事後選択である。

**修復されなかった例：`UR01-R05-R1-SELECT`（元資料E1-G58、保持役B）。** Aの最新版はrevision 3、紙ALL・デジタルNOT_ALL。ところが選ばれたのはGROUPに残っていたrevision 1、紙NOT_ALL・デジタルALLだった。保存器は指定された旧行を正確に複製し、READもそれを正確に抽出した。その結果、最新ならPAPERとなる案内がDIGITALになった。この材料では両方式・両反復の4系列とも同じ旧行が残った。

**正答に隠れた巻戻り：`UR01-G03-R1-SELECT`（元資料E1-G01、保持役B）。** 保存済みのAはrevision 4、紙ALL・デジタルALL。遅れて届いたrevision 3では紙ALL・デジタルNOT_ALLで、その旧通知が共同A欄へ採用された。それでもBとの組合せで案内はPAPERのままだった。READは保存された値に忠実で、最新案内とも一致したが、共同ノートの版・値・出典は古くなっている。後続までの完全一致では不成立と数えた。

別の修復例 `UR01-R02`（元資料E1-G31、保持役B）では、PRIVATE本人観測は最新のまま保たれ、REWRITEのGROUP本人行だけが両反復で旧版に残った。SELECTは両反復で最新に揃った。同じ個別・共同ノートでも、欄ごとの状態を分けて追う必要がある例となった。

## 6. 今回で分かったことと、次の一手

今回成立したのは、**受理された保存物を、その中の誤った旧版も含めて、忠実に後続へ運べたこと**。受理例の本人情報保持も成立した。一方、更新工程には「外側の形式」と「どの版を採るか」の二つの課題が残った。READの成功だけで更新成功を代表させると、今回の巻戻り1件を見逃す。

次は大きく再走する前に、**外側のコードブロックだけを扱う決定論的な受け口を、小さく設計・オフライン検証する**のを推奨する。すでに37件の実標本があるため、新たなLLM生成なしで、許す囲い・拒否する曖昧形・原文と処理履歴の保存を具体化できる。内側の構造検査と内容評価はそのまま残す。

併せて、この37件の内側を別枠で意味診断すれば、次の取得でまず扱うべき問題が、形式で隠れていた版選択なのか、別の記述不備なのかを絞れる。これは今回の正式成績の変更や、未実施READの補完とは分けて行う。その後、旧行保持・遅配採用に対して、LLMが選ぶ契約を見直すか、同一人物内の最大revision選択を機械側へ渡すかを判断する。
